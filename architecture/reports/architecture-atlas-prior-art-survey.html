Prior-art & literature survey

Field notes for a compiler's atlas

Metel-core issues #1159 (Atlas design), #1154 (shared spec-with-traceability framework), and #1156 (Architecture Atlas) call for a public, generated map from a stable requirement ID (arch.resolution.requirement-1) through owning code, verifying tests, and prior decisions — and back. This surveys who has solved pieces of that problem before, and what each piece is worth borrowing before any pixel is drawn.

1 · Documentation-as-code & the pipeline view

Three projects treat architecture description the way Metel already treats RFCs: a plain-text, versioned artifact that sits beside the code it describes, at a zoom level chosen for the reader rather than for the author.

C4 model
Simon Brown, 2006–2011 · c4model.com

Four fixed zoom levels — Context, Container, Component, Code — so "the pipeline view" and "stage details" are the same model read at two levels, not two separate diagrams to keep in sync.

pipeline viewstage details
c4model.com →
Structurizr
Simon Brown · reference C4 tooling

A DSL, not a drawing tool: one text model renders every C4 view. Diagrams are a build artifact of the model, so they can't drift from it the way a hand-drawn PNG does.

diagrams-as-codefreshness
docs.structurizr.com →
arc42
Starke & Hruschka, 2005 · arc42.org

Twelve fixed sections (context, building blocks, runtime, deployment, decisions…), plain Markdown/AsciiDoc, reviewed through the same pull-request flow as code. A template for the writing discipline, not the rendering.

structurestage details
arc42.org →
rustc-dev-guide
rust-lang · living guide

The closest in-kind precedent: a real compiler's own pipeline, written for contributors, with a chapter per stage (parsing, HIR, the query system, MIR) and a dedicated page on how queries memoize and depend on one another — the exact shape of Metel's own pipeline/stage-boundary story.

pipeline viewprecedent-in-kind
rustc-dev-guide.rust-lang.org →

2 · Traceability & governance

The arch-*/PROC-* ID scheme — status, owner, implementing paths, verification evidence, forward and reverse links — is not a new invention. It's the requirements- traceability matrix from safety-critical engineering, worn down to a size a compiler project can actually maintain.

DO-178C traceability
RTCA · airborne software certification

Defines the bar precisely: forward traceability proves every requirement is implemented and tested; backward traceability proves every line of code and every test is justified by a requirement. #1154's "forward and reverse traceability" is this, scaled down.

traceability viewthe strict definition
parasoft.com →
MADR / log4brains
adr.github.io · docs-as-code ADRs

ADRs as small Markdown files with a status field, built into a static site by a CLI (log4brains build). Directly reusable shape for #1158's ADR triage and for how an arch-* requirement file itself should look.

ADR lifecycleID scheme
adr.github.io →
Fitness functions
Building Evolutionary Architectures, Ford/Parsons/Kua, 2017 · ArchUnit

An architecture rule becomes a CI-run assertion, not a paragraph someone might read. "Health" in that world literally means: how many fitness functions are currently green. Directly names what #1154's checker and #1156's health view should compute.

health viewchecker design
mikaelvesavuori.se →
Backstage Soundcheck
Spotify · scorecard plugin

Consolidates scattered health signals — checks, standards, ownership — into one scorecard per component, drillable to the specific failing check. The closest working analogue to "which arch-* requirements are implemented / partial / lack evidence" as a single glanceable view.

health viewdashboard pattern
backstage.spotify.com →

3 · Code intelligence & the data-model view

A data-model view needs to answer "who produces this table, who reads it, under what invariant" for structures like TypedModuleGraph or ResolutionMap. That's a fact-database problem before it's a diagram problem.

Glean
Meta, open-sourced 2024

Stores typed, schema-defined facts about code — definitions, references, call graphs, type hierarchies — queried with a Datalog-style language (Angle). The right mental model for what #1154's checker output actually is: a fact table, not a folder of Markdown.

data-model viewchecker design
engineering.fb.com →
CodeSee maps
codesee.io

Auto-generated, self-updating dependency maps that show both upstream and downstream neighbors of a file or service — the "click a node, see what feeds it and what it feeds" interaction the pipeline view needs at its own scale.

pipeline viewinteraction
codesee.io →
cargo-modules / cargo-depgraph
crates.io

Already extract a Rust crate's module tree and inter-module dependency graph as Graphviz/JSON, today, with no bespoke parser to write. See §6 — this is a real build-vs-buy fork, not background reading.

github.com/regexident/cargo-modules →

4 · Rendering & interaction patterns

None of the above dictate how a page actually looks. These four are where the click-through feel and the diagram-freshness guarantee come from.

Redoc
Redocly · OpenAPI docs

Three-panel layout — nav, prose, live example — that stays legible with deeply nested schemas. A working answer to "traceability view" as a UI, not just a graph.

traceability viewlayout
redocly.com →
Mermaid / D2
text-to-diagram

Diagrams as a diffable text file, rendered at build time — the same "docs-as-code" discipline arc42 asks for, applied to the pictures instead of just the prose.

github.com/mermaid-js/mermaid →
Backstage TechDocs
Spotify, open-sourced

Markdown beside the code it describes, built into a static site, discoverable from the same catalog entry as the service itself — validates keeping the Atlas inside the existing Docusaurus site rather than a separate app.

From the literature

Living Documentation
Cyrille Martraire, 2019

Names the discipline this whole umbrella is: documentation generated from the same source of truth as the running system, so it cannot silently drift the way prose written once and forgotten always does. The philosophical case for #1141's whole premise.

overall approach
Building Evolutionary Architectures
Ford, Parsons & Kua, 2017

Introduces fitness functions as the unit of architectural governance — an assertion an architecture must keep satisfying as the code changes, checked the same way a unit test is.

5 · Recommendations, by Atlas view

What each Atlas view should borrow, stated as a decision rather than a survey. The first pass named five views; the evolved model adds full Decisions and Limitations registers while keeping Health cross-cutting.

ViewBorrow fromConcrete recommendation
Pipeline C4 (zoom levels) + rustc-dev-guide (per-stage chapters) + Mermaid/D2 Two fixed zoom levels only — the whole pipeline (Container-equivalent) and one stage drilled in (Component-equivalent) — generated from a text model, not hand-placed boxes, so a new stage or renamed representation can't leave the diagram stale.
Data-model / identity Glean (fact schema) + CodeSee (up/downstream) Keep each durable model concept as a persistent DATA-* fact record — producer, owner, consumers, mutation rule, invariants, code bindings, and explicit up/down neighbors. Generated code facts validate and enrich the record; they do not replace its stable identity or prose.
Traceability DO-178C (the strict definition) + Redoc (three-panel layout) Nav (requirement list) → prose (the requirement) → evidence panel (implementing paths, verifying tests, related ADRs/RFCs), with the same panel reachable by clicking from a code path back to its requirement — genuinely bidirectional, not a one-way index.
Stage details arc42 (fixed section template) + C4 Component level One fixed template per stage — API, owned data, allowed dependencies, contract tests, open limitations — so every stage page is scannable the same way regardless of who wrote it.
Health Soundcheck (scorecard) + fitness functions (what "health" counts) One scorecard: counts of implemented / partial / planned / missing-evidence, drillable straight to the offending requirement — not a prose summary of the same numbers.
Decisions MADR/log4brains (statused docs) + the RFC viewer (record-browser interaction) Render the complete ADR collection, not a cited-only subset: search, status facets, stable deep links, related/successor links, source metadata, and “cited by in this Atlas” reverse indexes. Reuse the RFC viewer’s interaction model while preserving ADR-specific lifecycle vocabulary.
Limitations Soundcheck (actionable health) + requirements traceability Give LIMIT-* records a dedicated viewer with lifecycle, ownership, acceptance, issue/successor-arch-* links, verification evidence, and a reconciliation queue. Health links into this work queue; it does not replace the limitations register.

6 · Buy vs. build: don't write a Rust parser first

Concrete, not just informational

cargo-modules already emits a crate's module tree and internal dependency graph; cargo-depgraph already emits inter-crate dependencies via cargo metadata — both as structured output, both maintained, both free. #1154's checker and #1156's pipeline/data-model views need exactly this kind of graph as an input.

Before #1154 writes a bespoke source-scanner for the module graph half of its job, it should confirm whether wrapping one of these (or feeding their output into the marker/traceability layer) gets most of the way there. The arch-* marker discovery and evidence-checking logic is genuinely novel and has to be built regardless — the raw dependency graph underneath it may not.

7 · Reuse survey: build the domain layer, reuse the machinery

The Atlas now has an authoritative Architecture Spec, persistent DATA-* facts, full ADR and limitation registers, and generated code facts. No single open-source project supplies all of that. The practical boundary is to own Metel's domain semantics and reuse diagram, indexing, traceability, and site machinery where it is a genuinely better fit than bespoke code.

LikeC4
MIT · architecture-as-code DSL and model API

A strong candidate for Context/Container/Component rendering: one source model, arbitrary nested levels, generated interactive views, a CLI, and a programmatic model API. Use it as a generated diagram target from the authoritative Atlas model, not as a second source of truth for arch-*, DATA-*, or LIMIT-*.

adopt / spikediagram renderer
likec4.dev →
FINOS CALM
Apache-2.0 · Common Architecture Language Model

A machine-readable, version-controlled architecture-model specification with CLI, visualization, and validation work. It is worth evaluating as an interchange or export target for topology and controls, not yet as the Atlas's primary representation: it does not model Metel's language rules, requirement evidence, or limitation reconciliation.

evaluateinteroperability
calm.finos.org →
StrictDoc / Sphinx-Needs
open-source requirements and traceability tooling

Both model linked, statused engineering objects and generate traceability views. StrictDoc additionally offers custom fields, source traceability, and static exports; Sphinx-Needs provides a generic linked-object/reporting model. They are high-value checker and schema precedents, but adopting either wholesale would add a parallel documentation stack beside MDX/Docusaurus.

borrow semanticstime-boxed spike
strictdoc →
Frictionless Data Package
open-source declarative tabular data validation

A close fit for the registry's baseline relational integrity: checked-in tables can declare primary keys, foreign keys, enums, and required fields, then validate through a CLI and produce an ER diagram. It can reject dangling arch-*, DATA-*, LIMIT-*, ADR, and evidence links without a bespoke validator.

adopt / evaluatereferential integrity
framework.frictionlessdata.io →
Soufflé Datalog
open-source declarative relation-analysis engine

The candidate rule engine once validation goes beyond foreign keys: reverse traceability, missing evidence, successor paths, and limitation reconciliation are naturally expressed as relations and rules, not Python control flow. Soufflé reads facts from flat files or SQLite and emits derived relations such as the Health and reconciliation queues.

adopt / evaluatedeclarative policy
souffle-lang.github.io →
OpenFastTrace
GPL-3.0 · Markdown-to-source tracing suite

Close to the proposed marker/checker path: it traces tagged Markdown specification items into source and reports coverage in CI. It may be useful as a standalone checker comparison or spike; its Java runtime, GPL license, and separate report UI make it a poor replacement for the Atlas viewer without a deliberate license review.

evaluate carefullychecker
github.com/itsallcode/openfasttrace →
SCIP / Glean
open code-intelligence index formats and fact store

Suitable for the generated code-fact layer: symbol locations, references, call relationships, and type relationships can power navigation and validate DATA-* bindings. Glean and Kythe are operationally substantial; SCIP is the lighter interoperability seam to assess before building a custom index.

reuse / evaluatecode facts
scip-code.org →
Backstage catalog
open-source entity catalog and relationship graph

A useful model for stable entities, typed relations, ownership, filters, and graph traversal. Do not adopt the full developer portal for this scope: its catalog is designed to integrate and cache external sources, while the Architecture Spec and registries must remain the Atlas's versioned authority.

borrow interactiondo not adopt whole
backstage.io →
Recommended composition

Keep the Architecture Spec plus arch-*, DATA-*, and LIMIT-* registries as the versioned source of truth. Normalize their cross-record data into a declarative package: entities, typed links, code bindings, evidence, limitation resolutions, and issue snapshots. Use a relational schema and foreign-key validation for baseline integrity; use Datalog only for derived policies such as reverse traceability, Health, and limitation reconciliation. Generate Atlas JSON through a Docusaurus plugin, reuse cargo tooling and possibly SCIP for code facts, and run a short LikeC4 spike for topology rendering. Treat CALM, StrictDoc, Sphinx-Needs, and OpenFastTrace as interoperability or checker evaluations rather than migrations by default.

8 · Carried into the mockups

Not answered here — #1159's design pass should settle these before implementation, per its own scope note on reuse.

?Do the Architecture Atlas and the future Process Atlas share one visual language for a "requirement card," or does PROC-* get its own treatment once #1142 is scoped? #1159 flagged this but didn't resolve it.
?Is the pipeline-view diagram rendered at build time as static SVG (Mermaid/D2 in CI, matching the site's no-backend principle) or client-side from JSON (closer to CodeSee's live-feeling interaction)? The two imply different libraries and different bundle costs.
?Does the health view need per-requirement history (a fitness function that regressed last week), or is a current-state snapshot enough for v1? Soundcheck and ArchUnit both default to snapshot; history is a real second phase, not a v1 requirement.
