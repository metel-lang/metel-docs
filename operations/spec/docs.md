# Documentation

Where the documentation lives, how it is pinned and generated, and the lifecycles it follows. Source: ADR-0051, ADR-0055, ADR-0057, ADR-0064, `metel-docs/architecture/PROCESS.md`, `metel-docs/rfcs/PROCESS.md`.

### PROC-DOCS-001 — metel-docs is the single public documentation source and is edited directly {#proc-docs-001}

There is no mirror and no sync step. Private reports and strategy material live in `metel-docs-internal`, which has no CI and is never built into the site.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | every documentation change |
| `produces` | the language reference, RFCs, ADRs, the Architecture Spec, tutorials, blog posts, release notes and this specification |
| `implemented by` | `metel-docs` (trunk-based `main`, changes by pull request); ADR-0051 |
| `verified by` | the four workflows of PROC-CI-003 |
| `related` | PROC-DOCS-002 |

### PROC-DOCS-002 — Each consumer pins the docs by its own pointer {#proc-docs-002}

The two pointers are independent and move at different times. Core's moves when core work needs new docs content, and at a release (to the tip of metel-docs `main`). The website's moves at a release (to core's pin), and the unreleased view advances it to `main` for its own build. The released site reads versioned snapshots, not the pointer.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | a change to `metel-docs` that a consumer must see |
| `produces` | a consumer reading an exact docs commit |
| `implemented by` | `metel-core` `docs` gitlink; `metel-website` `docs` submodule pointer |
| `verified by` | none automated for the pointers; PROC-DOCS-003 moves core's, PROC-RELEASE-003 and PROC-DEPLOY-004 move the website's |
| `related` | PROC-DOCS-003, PROC-RELEASE-003, PROC-DEPLOY-004 |

### PROC-DOCS-003 — Core's docs gitlink is moved by one command and a pull request {#proc-docs-003}

The tool never merges. It stops when the pin already points at the target, refuses a dirty tree or an existing branch, and runs the checks that read docs on the new commit first. The pin may otherwise lag metel-docs `main`; the release records the exact commit.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | manual: `tools/bump-docs.sh`, when core work depends on new docs content (a claim id, a spec rule a fixture cites, a tool change) |
| `produces` | a branch `chore/bump-docs-<sha>` that moves the gitlink, and a pull request to `develop` listing the docs commits |
| `implemented by` | `metel-core/tools/bump-docs.sh` |
| `verified by` | `tools/test_bump_docs.sh`, run by the `tools self-tests` job |
| `related` | PROC-DOCS-002, PROC-CI-002 |

### PROC-DOCS-004 — Architecture evidence is generated when documentation is published, never committed {#proc-docs-004}

In `metel-docs` the cells hold `_Generated at publish._`, a limitation record carries no generated block, and the hand-written `path::symbol` bullets of `## Affects` are unlinked. Hand-authored content stays: the requirement text, exemptions, and `last_reviewed`. The checker never compares a placeholder.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | publishing: PROC-RELEASE-005 for a release, PROC-DEPLOY-004 for the unreleased view |
| `produces` | the `implements` and `verified by` links of every requirement, and the code links of limitation records, pinned to a release tag (or a `develop` commit) |
| `implemented by` | `metel-docs/architecture/tools/generate_architecture_evidence.py` (`--publish`); ADR-0064 |
| `verified by` | core CI job `Architecture evidence` (meaning, PROC-CI-001); the tool's tests; the placeholder migration reproduced the earlier rendering exactly (110 rows, 65 records) |
| `related` | PROC-RELEASE-005, PROC-DEPLOY-004, PROC-CI-002 |

### PROC-DOCS-005 — Generated documentation is checked in CI, and regenerated by a person {#proc-docs-005}

Generation is explicit and checking is automatic: CI never rewrites content, it checks that the committed output equals a fresh run. Anything a reader sees that the repository does not store (record lists, health figures, pipeline text, search data) is computed from committed files when the site is built. Derived text is generated; a human judgment is written by hand.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | a change to the sources of a generated page |
| `produces` | the pages below, equal to a fresh run |
| `implemented by` | `gen_grammar` (writes `reference/spec/grammar.md`); `rfc.py index --write-spec-origins` (the "Referenced by" and "Tested by" blocks of the spec and the fixtures list of `error-codes.md`); `rfc.py index --rebuild-registry` and `--write-coverage-baseline` (`rfcs/REGISTRY.md`, `rfcs/COVERAGE-BASELINE.json`); `check_stdlib_docs` checks `reference/spec/runtime.md` against the stdlib declarations |
| `verified by` | core CI jobs `grammar.md up to date` and `runtime.md matches stdlib declarations`; `rfc.py check` and `rfc.py index --check-drift` |
| `related` | PROC-CI-001, PROC-DOCS-004 |

### PROC-DOCS-006 — A review of a claim is a hand-typed commit, audited, and enforced at release {#proc-docs-006}

`last_reviewed` is never written by a tool: a field a tool could refresh would give no forcing function. A tool only reports that the cited code or fixture changed after the recorded commit, or that the recorded commit is not reachable (core merges by rebase, so a recorded commit can vanish). A missing marker is a shape error and fails a pull request.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | a change to code that a requirement cites, or a citing fixture of a spec rule |
| `produces` | a warning on the pull request; a failure at release |
| `implemented by` | `generate_architecture_evidence.py` (the `last_reviewed` row of a requirement), `rfc.py` (the `<!-- rfc.py:last_reviewed SHA -->` comment of a spec rule); both with `--strict` |
| `verified by` | the tools' tests; `/cut-release` runs both with `--strict` |
| `related` | PROC-RELEASE-008, PROC-CI-005 |

### PROC-DOCS-007 — Spec text that runs ahead of the code carries a Pending marker {#proc-docs-007}

Valid while the issue is open and has a milestone. A closed issue makes the marker stale and fails the check. The release gate refuses a tag while a marker or fixture cites an issue still open in the release milestone, one with no milestone, a missing one, or one it could not verify. The record kinds Gap and Limitation are reserved for what is deliberately left in a released version.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | spec text lands before the code that implements it, in the same milestone |
| `produces` | the line `> **Pending** metel-core#N`, or a fixture `skip = "pending: #N"` |
| `implemented by` | `metel-docs/architecture/tools/check_architecture.py` (`check_pending_markers`, `--release-gate`); the site renders it (`spec-limit-markers.mjs`); `reference/spec/STYLEGUIDE.md` |
| `verified by` | the tool's tests; `architecture-check` and core CI resolve the issue's state; `/cut-release` runs the release gate |
| `related` | PROC-RELEASE-008, PROC-DOCS-009 |

### PROC-DOCS-008 — RFCs move through stages by tool, and the directory is the state {#proc-docs-008}

No implementation starts below the integrated stage. Moving to integrated needs a tracking issue; the check requires `tracking` from under review and `impl_tracking` from integrated. `rfc.py check` reports problems, which fail, and freshness warnings, which do not (PROC-CI-005).

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | `rfc.py new`, `rfc.py transition`, `rfc.py supersede` |
| `produces` | an RFC file in the directory that names its stage, with frontmatter that agrees |
| `implemented by` | `metel-docs/rfcs/tools/rfc.py`, `metel-docs/rfcs/PROCESS.md` |
| `verified by` | `rfc.py check` in `rfc-check.yml` and in core CI; `rfcs/tools/test_rfc.py` |
| `related` | PROC-CI-005 |

### PROC-DOCS-009 — Gaps and limitations are records with a lifecycle {#proc-docs-009}

The sorting test asks whether a fully correct implementation of the current spec would still behave this way (Gap) or the spec promises more than the code delivers (Limitation); if the spec is clear and the code is wrong it is a bug and an issue. A record is reproduced on `develop` before it is written. Known weakness: `planned_for` still names retired version numbers (metel-core#1525).

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | a deliberate boundary of the spec (Gap), or a shortfall of the implementation against it (Limitation) |
| `produces` | a record under `architecture/gaps` or `architecture/limitations`, cited from the chapter by one marker line |
| `implemented by` | `metel-docs/architecture/tools/check_architecture.py`; ADR-0055, ADR-0057 |
| `verified by` | `architecture-check` and core CI; `test_check_architecture.py` |
| `related` | PROC-DOCS-007 |

### PROC-DOCS-010 — Examples in the documentation are executed {#proc-docs-010}

The checker is fetched fresh from core `develop` by the other repositories, so there is nothing to keep in sync by hand.

| Field | Value |
|---|---|
| `status` | `implemented` |
| `owner` | documentation |
| `trigger` | pull request or push to the repository that holds the examples |
| `produces` | a pass or fail per fenced example; `skip` and `expect-fail` markers exempt an example on purpose |
| `implemented by` | `metel-core/tools/check_doc_examples.py`, run by core CI (`doc examples`: `README.md` and the docs), by `metel-docs` `check-examples` (against core's rolling binary, PROC-CI-004) and by `metel-website` `check-showcases` |
| `verified by` | the three workflows; `release-notes` and `rfcs` are excluded on purpose because they document rejected or not-yet-built syntax |
| `related` | PROC-CI-004, PROC-DEPLOY-007 |

### PROC-DOCS-011 — Documentation pages compile as MDX before they reach the site {#proc-docs-011}

The check does not build `architecture`, `operations`, `rfcs` or `status`, so an MDX error there is first seen by the website build. Its vendored site configuration can also drift from the website's real one (metel-core#698).

| Field | Value |
|---|---|
| `status` | `partial` |
| `owner` | documentation |
| `trigger` | pull request or push to `metel-docs` `main` |
| `produces` | a pass or fail from a minimal Docusaurus build |
| `implemented by` | `metel-docs/.github/workflows/check-mdx.yml`, `metel-docs/tools/mdx-check-site` |
| `verified by` | the workflow builds `getting-started`, `reference`, `release-notes` and `blog` |
| `related` | PROC-CI-003 |

### PROC-DOCS-012 — The spec fixture viewer embeds the fixture source {#proc-docs-012}

Embedding grows every published version. The intended end state is to fetch the source lazily from GitHub when the block is opened (metel-core#1499).

| Field | Value |
|---|---|
| `status` | `partial` |
| `owner` | documentation |
| `trigger` | regeneration of the "Tested by" blocks (PROC-DOCS-005) |
| `produces` | a collapsible block per citing fixture holding a base64 snapshot of the `.mtl` source |
| `implemented by` | `metel-docs/rfcs/tools/rfc.py`; `metel-website` spec-fixture swizzle |
| `verified by` | `rfc.py check` (drift) |
| `related` | PROC-DOCS-005 |
