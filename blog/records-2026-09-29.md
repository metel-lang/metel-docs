The [first post](/blog/introducing-metel) said records would get their own writeup
once the design was further along. It is — and the design changed on the way. So
this is both the promised post and a correction to it.

## The bridge that isn't there

In July the plan was a bridge. A struct would opt into a structural view with a
derive, expose its fields as a row, and take them back again:

<!-- doc-example: skip reason="the abandoned July design, not valid Metel" -->
```metel
#derive(ToRecord, FromRecord)
struct Handle { fd: i32, label: String }

let row: record { fd: i32, label: String } := handle.to_record();
let handle2 := Handle::from_record(row);
```

`ToRecord` to get the row out, `FromRecord` to put it back. The point was partial
consumption — letting the program say *this field is gone, these are still here* —
with `Rc` / `Arc` teardown as the case that needs it.

None of that got built, because building it made the bridge look redundant. A
struct doesn't need to be converted to a row. It is one.

## Every struct is a branded row

A struct declaration is two things: a row of fields, and a *brand* — a nominal
identity that says "this row is a `Handle`, and it is not interchangeable with
some other row that happens to have the same fields." The row and the brand come
apart. You can project a sub-row and keep the brand:

```metel
struct Handle { fd: i32, name: String }

fun main() {
    let h := Handle { fd = 3, name = "log" };
    let just_fd: Handle.{ fd } := h.{ fd };
    assert(just_fd.fd == 3);
}
```

`Handle.{ fd }` is a *residual*: the `Handle` brand, narrowed to one field. It is
not an anonymous record — it still carries the identity, a parameter written
`Self.{ fd }` accepts it, and projecting it back to full width normalizes to plain
`Handle`.

## Partial moves narrow the type

The thing the bridge was for now just happens. Move a non-`Copy` field out of a
struct and the value's static type narrows to the residual:

```metel
struct Handle { fd: i32, name: String }

fun read_fd(fd: i32) -> i32 { fd }

fun main() {
    var h := Handle { fd = 3, name = "log" };
    let taken := h.name;         // h : Handle.{ fd } — `name` moved out
    assert(read_fd(h.fd) == 3);  // fine, fd is still there
    h.name := "reopened";        // h : Handle again
    assert(h.name == "reopened");
}
```

This is a type-checker fact, not a lint. After the move, `h`'s type *is*
`Handle.{ fd }`, and using it where the whole `Handle` is required is an error:

<!-- doc-example: expect-fail reason="using a partially-moved value as a whole is the point" -->
```metel
struct Handle { fd: i32, name: String }

fun persist(h: Handle) -> i32 { h.fd }

fun main() {
    var h := Handle { fd = 3, name = "log" };
    let taken := h.name;
    persist(h);   // T0001: a partially-moved `Handle` (now `Handle.{ fd }`)
                  //        cannot be used where the whole `Handle` is required
}
```

The narrowing is path-sensitive: each `if` / `match` arm forks from the state
before it and the arms rejoin afterward, so a move on one arm narrows `h` for the
code after the `match`, and a later arm never inherits an earlier arm's move.
`--move-check` is in on it too — using `h` at its narrowed type isn't flagged as a
partial-move violation, because at that type it isn't one.

A `Copy` field read by value doesn't narrow anything — copying `fd` out leaves `h`
a whole `Handle`. Only a move takes a field away. If the binding owns its value,
putting the field back widens the type again, as `h.name := "reopened"` did above.
No `FromRecord`, no constructor call: ordinary field assignment already bypasses
constructor invariants, and widening rides on that and adds nothing.

Move the *last* non-`Copy` field and what is left is the empty residual. It keeps
the brand, can be passed and returned, and widens again on reassignment; `Token.{}`
names it:

```metel
struct Token { text: String }

fun consume(s: String) -> i64 { 1 }

fun main() {
    var t := Token { text = "abc" };
    let s := t.text;               // t : Token.{}
    let spent: Token.{} := t;      // the brand outlives the last field
    assert(consume(s) == 1);
}
```

## The Rc case, and where it stops

The motivating example from the first post was `Rc` / `Arc`: when the last strong
reference goes, the payload has to be destroyed while the allocation and the
counts stay live until the weak references are gone too. Inside a function that
owns the box, that decomposition is exactly the narrowing above:

```metel
struct RcBox<T> { strong: i64, weak: i64, value: T }

fun log_counts(strong: i64, weak: i64) -> i64 { strong + weak }

fun into_value<T>(box: RcBox<T>) -> T {
    let v := box.value;          // box : RcBox<T>.{ strong, weak }
    log_counts(box.strong, box.weak);
    v
}

fun main() {
    assert(into_value(RcBox { strong = 1, weak = 2, value = 7 }) == 7);
}
```

`box.value` moves out; `box` is now `RcBox<T>.{ strong, weak }`, and the counters
stay readable and correctly typed for the rest of the body.

Two pieces of the real thing aren't here yet, and it's worth being precise about
which:

- **Decomposition through a `&var`.** `Rc::drop_slow` doesn't own the box — it
  works through `&mut self`. Metel rejects moving a field out of a reference at
  all: a reference grants access, never ownership. The narrowed receiver that
  would make it sound — projecting `&var self` down to `&var Self.{ strong, weak }`
  — is RFC-0137 §5. It did not make v0.14.0; it is scheduled for v0.16.0. Until
  then, field-sensitive ownership *through a borrow* is still an open edge.
- **`Drop` dispatch on a residual.** A type with a `Drop` impl currently can't be
  partially moved at all, for the same missing-narrowed-receiver reason. So the
  pattern works for a box you tear down explicitly, not one with a destructor.

## "I only touch these fields", generically

The other half of the first post's motivation was the generic version — a function
that wants *any value with an `x` and a `y`* without naming a type. That's a row
bound:

```metel
fun magnitude_sq(p: { x: f64, y: f64, .. }) -> f64 {
    p.x * p.x + p.y * p.y
}

fun main() {
    assert(magnitude_sq({ x = 3.0, y = 4.0 }) == 25.0);
    assert(magnitude_sq({ x = 3.0, y = 4.0, z = 9.0 }) == 25.0);
}
```

`..` makes the row open: *at least* these fields. Drop it and the bound is closed —
exactly these, nothing else. When you need to name the argument's type, to hand the same
value back for instance, declare it: `fun reset<record T: { x: f64, .. }>(p: T) -> T`. A field can pin the label without a type
(`{ x, y: f64, .. }`), and a bound can be negative per field: `!{ token }` accepts
any record with no `token` label at all, `!{ x: f64 }` accepts one whose `x` is
some other type.

A plain struct never satisfies a row bound. The brand is the whole reason a struct
is nominal; erasing it silently to slot into a structural bound would defeat the
point. So struct data flows through row-bounded code by handing over the fields
explicitly — there's no implicit struct-to-row coercion, by design.

## Prior art: Niko's view types

Everything in the last few sections has a close relative that I should name properly:
Niko Matsakis's series on view types for Rust. It runs through
[View types for Rust][vt1] (2021), [View types redux and abstract fields][vt2] (2025),
[Maximally minimal view types][vt3] (March 2026) and its [follow-up][vt4]. The 2021 post
is the comparison I wrote my first self-view RFC against, and it is where the problem
is stated best: a function that touches one field shouldn't have to give up the whole
value. His example is moving `self.bars` out and then being unable to call a method that
only reads `self.golden_tickets`.

His answer is a view type, written `{ golden_tickets } Manifest` in the first two posts
and `Manifest.{ statistics }` after the follow-up swapped braces for a dot: the struct,
with only some fields accessible. Metel's residual `Handle.{ fd }` is the same idea, and
the overlap goes further than the name. His 2025 post moves two fields into a view and
keeps using the third:

<!-- doc-example: skip reason="Rust-syntax sketch from the 2025 post, shown for comparison" -->
```text
let t: {a, c} Strings = {a, c} s;   // s.b stays usable, t.b is an error
```

The same program in Metel:

```metel
struct Strings { a: String, b: String, c: String }

fun main() {
    let s := Strings { a = "a".to_string(), b = "b".to_string(), c = "c".to_string() };
    let t: Strings.{ a, c } := s.{ a, c };   // moves a and c out of s
    assert(s.b == "b");                      // the rest of s is still usable
    assert(t.a == "a" && t.c == "c");        // t.b would be an error
}
```

His March follow-up ends on returning a partly initialised value after a field has been
dropped, which he calls "neat". That already works as a plain partial move:

```metel
struct Stats { n: i64 }
struct Processor { messages: String, statistics: Stats }

fun take_statistics(p: Processor) -> Processor.{ messages } {
    let st := p.statistics;   // p : Processor.{ messages }
    p
}

fun main() {
    let p := Processor { messages = "m".to_string(), statistics = Stats { n = 1 } };
    let q := take_statistics(p);
    assert(q.messages == "m");
}
```

The refusal to coerce is shared too. He leaves out the rule that would let a whole value
stand in for a view, because it would make `let t: {a, c} Strings = s;` compile. Metel
rejects the same thing: a whole `Strings` is not accepted where `Strings.{ a, c }` is
required, and narrowing only ever happens through an explicit move or projection, never at
a call boundary.

Where I differ, or where I am behind him, matters more than where I agree:

- **His series is mostly about borrows; my residuals are mostly about moves.** In his
  proposal the call site builds the view for you (`&mut *self.{ statistics }`) and the
  borrow checker records one loan per field. Metel has no equivalent. A parameter of type
  `&Self.{ fd }` accepts a value that has already been narrowed, but I can't lend a
  sub-row of an owned value without moving the fields out, and a method can't yet declare
  a narrowed `self`. That is deliberate. Partial borrows only mean something once there is
  a borrow checker to enforce them, and Metel's is still a design (RFC-0122), so I built
  the move half first and left this one for later. It is the `&var` row in the table
  below, and his posts are the best map I have of what filling it in looks like.
- **A projection here is a move.** `h.{ name }` moves a non-`Copy` field out and keeps the
  brand on what it hands back, rather than borrowing a view. That is a consequence of the
  borrow half not existing yet, and I'm treating it as an open design question, not a
  settled one.
- **Generics go through open rows.** He defers inference of field sets, mentioning row
  polymorphism as one route. Metel took that route early, which is what the `..R` sections
  above are.
- **Privacy.** He proposes abstract fields so a public signature need not name private
  ones. I have no counterpart: a `record` publishes every field, and a struct's residual
  can only name fields visible where it is written.

I don't want to present any of the overlap as independent invention. The shape of the
problem, the view-type framing, the partial-move example, and the dot spelling are in his
posts, and all four predate Metel's first commit (March 30, 2026; the newest was
published a week before that). If you came here for the idea itself, read his series
first.

[vt2]: https://smallcultfollowing.com/babysteps/blog/2025/02/25/view-types-redux/
[vt3]: https://smallcultfollowing.com/babysteps/blog/2026/03/21/view-types-max-min/
[vt4]: https://smallcultfollowing.com/babysteps/blog/2026/03/22/max-min-view-types-followup/

## Records with no brand to begin with

Data that has a shape but no identity is its own type: `{ x = 1.0, y = 2.0 }` as a
value, `{ x: f64, y: f64 }` as a type.

- **Exact.** `{ x: i64, y: i64 }` and `{ y: i64, x: i64 }` are the same type;
  `{ x: i64 }` and `{ x: i64, y: i64 }` are not, and neither is a subtype of the
  other. There is no width subtyping — a record with an extra field is a different
  type, not a compatible one.
- **No inherent behaviour.** No methods of their own and no `Drop`. An anonymous
  record gets `Copy`, `Display`, `Clone`, `Send` and `Sync` from its fields, and an
  aspect can be implemented for a record shape, but a record cannot carry methods.
  If you want those attached, you want a brand.
- **They narrow the same way.** `let a := r.left;` leaves `r : { right: i64 }`.
  The only difference from a struct residual: there's no brand on what's left, so a
  stale whole-value use is an ordinary shape mismatch rather than a
  "partially-moved" diagnostic — same `T0001`, plainer wording.
- **`{ x }` in statement position is still a block.** Where it's ambiguous,
  parenthesize the record: `({ x = e })`. The diagnostic tells you so at the point
  of use.

## `record`: the brand you can see through

That leaves a gap. A struct has a brand but its row is invisible to row bounds. An
anonymous record has a visible row but no brand. v0.14.0 fills it with a named
record, written `record` instead of `struct`:

```metel
record Point { x: f64, y: f64 }

fun magnitude_sq(p: { x: f64, y: f64, .. }) -> f64 {
    p.x * p.x + p.y * p.y
}

fun main() {
    assert(magnitude_sq(Point { x = 3.0, y = 4.0 }) == 25.0);
}
```

A `record X { … }` is a `struct X { … }` in every respect — name, brand, identity,
construction, field access, coherence — except one: its declared row is
*structurally visible*. It satisfies row bounds and it is matched by row-conditional
impls. A plain struct still isn't:

<!-- doc-example: expect-fail reason="a plain struct never satisfies a row bound — the point" -->
```metel
struct Point { x: f64, y: f64 }

fun magnitude_sq(p: { x: f64, y: f64, .. }) -> f64 {
    p.x * p.x + p.y * p.y
}

fun main() {
    magnitude_sq(Point { x = 3.0, y = 4.0 });
    // T0012: `Point` is a struct, but a struct never satisfies a row bound;
    //        declare it as a `record` instead
}
```

Switching between the two keeps the name, brand, generic parameters and impls
unchanged, and whole-value call sites typecheck the same either way. `struct` to
`record` is additive: it only newly lets the type through row bounds. The cost is
that every field of a record is public, because publishing the row is what makes it
something other code may match on. So a record's fields are written bare, and
converting a struct publishes all of them, including any that were private;
converting back makes each one private again.

There is no way to make one record field private, and the compiler says so if you
try. Writing `public` on a record field is a syntax error, reported at the modifier:

<!-- doc-example: expect-fail reason="a public modifier on a record field is rejected — the point" -->
```metel
record Point {
    public x: f64,   // error: `public` is not written on field `x` of `record Point`:
                     // every field of a record is public, so a record field takes no
                     // visibility modifier -- remove `public` (declare a `struct`
                     // instead if `x` should stay private)
    y: f64,
}

fun main() {}
```

A record also gets field-wise built-ins. `Copy`, `Display` and `Clone` derive from
the fields, `Display` prints in label order and keeps the record's name, and a
struct doesn't acquire any of them just because its fields have them:

```metel
record Point { x: f64, y: f64 }

fun main() {
    let p := Point { x = 1.5, y = 2.5 };
    let q := p;                 // Copy, field by field
    println("${p} ${q}");       // Point { x: 1.5, y: 2.5 } Point { x: 1.5, y: 2.5 }
    let c := p.clone();
    println("${c}");
}
```

Field-wise `Eq`, `Hash` and `Ord` are deferred; they are not in this release.

## Open rows

An open row in a bound says *at least these fields*. v0.14.0 lets you name the rest.
`..R` is a row tail, `row R` declares a row parameter, and a function can promise
something about its tail without knowing what is in it. The case that shows what
this buys is a typestate: stripping a field off a record and putting it back,
where the compiler tracks what is left.

```metel
fun strip<row Rest>(d: { token: String, ..Rest }) -> { ..Rest } {
    let { token: _, ..rest } := d;
    rest
}

fun add_token<row R: !{ token }>(d: { ..R }) -> { token: String, ..R } {
    { token = "secret", ..d }
}

fun main() {
    let redacted := strip({ token = "t", user = 3 });
    assert(redacted.user == 3);
    let signed := add_token(redacted);
    assert(signed.user == 3);
}
```

Three things are new in that snippet. A row *tail* with other fields written beside it,
`{ token: String, ..Rest }`, says what the argument is made of, so the call derives `Rest`
instead of the caller supplying it. A *remainder pattern*, `..rest`, binds everything the
other patterns didn't take, as an owned row. And a *spread*, `{ token = "secret", ..d }`,
builds a record from one owned row, with the spread labels unable to overwrite explicit
fields. `add_token` is bounded by `!{ token }` so the label it adds cannot already be there.

When the row belongs to a named type there is nowhere to write the tail inline, and a row
*equation* says the same thing from the outside:

```metel
record Builder<row R> { name: String, data: { ..R } }

fun strip_auth<row R, row Rest>(b: Builder<..R>) -> Builder<..Rest>
where R = { auth: String, ..Rest } {
    let { name, data } := b;
    let { auth: _, ..rest } := data;
    Builder { name = name, data = rest }
}

fun main() {
    let b := Builder { name = "req", data = { auth = "tok", retries = 3 } };
    assert(strip_auth(b).data.retries == 3);
}
```

Throwing fields away is the part that needs a guard. Passing a record by value to
an open-row parameter *forgets* whatever the parameter doesn't name, and a forgotten
field has to be `Copy`, because otherwise nothing would own it afterwards:

```metel
fun get_x<row R>(p: { x: f64, ..R }) -> f64 { p.x }

fun main() {
    let r := { x = 1.0, count = 7 };   // `count` is Copy: forgetting it is fine
    assert(get_x(r) == 1.0);
}
```

<!-- doc-example: expect-fail reason="forgetting a non-Copy field is the point" -->
```metel
fun get_x<row R>(p: { x: f64, ..R }) -> f64 { p.x }

fun main() {
    let r := { x = 1.0, label = "gone".to_string() };
    let _ := get_x(r);
    // T0033: passing `{ label: String, x: f64 }` by value to an open row parameter
    //        forgets field `label` of type `String`, which is not `Copy` -- no owner
    //        would be left for it
}
```

A generic function can't see the fields of its own row, so it has to say what it
needs. `where all R: Copy` constrains every field of the row, open tail included,
and it can be forwarded through generic calls:

```metel
fun copy_twice<row R>(value: { ..R }) -> ({ ..R }, { ..R })
where all R: Copy {
    (value, value)
}

fun main() {
    let pair := copy_twice({ count = 5, label = 'x' });
    assert(pair.0.count + pair.1.count == 10);
}
```

Leave the bound out and `--move-check` reports the second use of `value` as a use
after move, because nothing says the row can be copied. The row can also be the row
argument of a named record: for `record Packet<row R> { data: { ..R } }`,
`where all R: Copy` works on a `Packet<..R>` parameter or on an `extend` for
`Packet<..R>` the same way.

## Matching

Struct patterns match named structs, and record patterns bind a remainder:

```metel
struct Token { kind: i64, span: i64, text: String }

fun handle(kind: i64, span: i64) -> i64 { kind + span }

fun main() {
    let token := Token { kind = 1, span = 2, text = "t" };
    let r := match (token) {
        Token { kind, span, .. } => handle(kind, span),
    };
    assert(r == 3);

    let { id, ..rest } := { id = 7, name = "a", age = 3 };
    assert(id == 7 && rest.age == 3);
}
```

One difference from the narrowing above is worth knowing before you hit it. Moving
fields out one at a time keeps the brand: after `let v := a.value;`, `a` is still a
`Token.{ id }`. A rest pattern does not. `..rest` binds a new anonymous record made of
everything the pattern didn't name, and the nominal brand stays behind.

```metel
record Token { value: String, id: i64 }

fun take(t: Token.{ id }) -> i64 { t.id }

fun main() {
    let a := Token { value = "x".to_string(), id = 1 };
    let v := a.value;                      // a : Token.{ id } — still a Token
    assert(take(a) == 1);

    let b := Token { value = "y".to_string(), id = 2 };
    let { value: _, ..rest } := b;         // rest : { id: i64 } — no brand
    assert(rest.id == 2);
}
```

Hand `rest` to something that wants the branded residual and the compiler says why:

<!-- doc-example: expect-fail reason="a rest-pattern remainder is anonymous, not a branded residual — the point" -->
```metel
record Token { value: String, id: i64 }

fun take(t: Token.{ id }) -> i64 { t.id }

fun main() {
    let b := Token { value = "y".to_string(), id = 2 };
    let { value: _, ..rest } := b;
    take(rest);
    // T0001: an anonymous record is not `Token.{ id }`: a record rest pattern (`..rest`)
    //        drops the nominal brand of what it destructures; move the fields out one at
    //        a time (`let v := value.field;`) to keep the branded residual
}
```

The same applies to dispatch: methods and aspect impls on `rest` are the ones for an
anonymous record, not `Token`'s.

Bare field bindings only for the moment — `Token { kind: 1, .. }`, a sub-pattern on a
field, isn't in yet. The trailing `..` is required unless the pattern names every
field, and naming a private field from outside the declaring module is rejected the
same as it is in construction.

## Where it lands

Scoring the first post's "closest thing to an open problem" against what's built:

| | status |
| --- | --- |
| owned decomposition | done — partial move narrows to a residual, reassignment widens it back |
| explicit projection | done — `v.{ a, b }` is a first-class sub-row that keeps the brand |
| generic "only these fields" | done — row bounds, open row parameters, equations, field-wise bounds |
| a nominal type you can match structurally | done — `record` |
| decomposition through a `&var` | **not done** — needs the narrowed receiver (RFC-0137 §5, v0.16.0) |
| `Drop` dispatch on a residual | **not done** — same missing receiver |

Still ahead: tuples as numeric-label rows (RFC-0151, a draft), field-wise `Eq`,
`Hash` and `Ord`, and the unified identity mechanism that a brand is one case of —
RFC-0159 is in review for it.

## Everything else since the first post

The first post went up on July 15. Between then and now there have been six
releases (v0.10.0 through v0.13.1) and this one. The records work is the thread I
care most about, but it is a small part of what changed. A short list, newest
last; the [changelog](/docs/release-notes/changelog) has the long version.

- **v0.10.0 (July 17) — the surface settles.** `public`, `var` and `extend` become
  the canonical spellings, references are `&T` and `&var T`, and the bottom type
  `!` is writable. On the type side: conditional aspect implementations are
  enforced, implementation coherence has orphan and overlap rules, negative bounds
  (`T: !Aspect`) and negative impls exist, associated types work, and a function can
  return `impl Aspect`.
- **v0.11.0 (July 24) — enums and references.** A match arm or an expression can
  name a variant without its enum prefix when the expected type is known, and
  `None`, `Some`, `Ok` and `Err` are ordinary variants rather than special
  literals. Reference rules were tightened, with breaking changes to assignment and
  write-through.
- **v0.12.0 (August 3) — anonymous records and the first ownership.** Anonymous
  records and row bounds arrive, `Copy` and `Drop` are declared in the standard
  library, and `--move-check` appears as an opt-in pass.
- **v0.12.1 (August 9) — interpreter-only fixes.** Negative bounds (`T: !Aspect`) are
  enforced for tuples, arrays and references too, and an aspect implementation must
  contain exactly the methods its aspect declares, with matching signatures.
- **v0.13.0 (September 6) — the closure cluster.** Closures and function types are
  written with pipes (`|x: i64| { x + 1 }`), closures take capture lists (`[x]`) and
  qualifiers, `:=` marks bindings that are kept, `type Name := T` gives a type an
  alias, `dyn Aspect` objects work, and partial moves narrow the type, which is
  where the narrowing in this post comes from.
- **v0.13.1 (September 27) — tooling.** Cross-module name-collision fixes, and the
  frontend APIs that the first release of `metel-lsp` is built on.
- **v0.14.0 — this release.** Named records and open rows, as above; array types
  written `[T]` and `[T; N]` with sized array literals inferred by default; and
  generic definitions checked against their declared bounds, so a generic body can
  use only what its bounds grant. The opt-in move checker now analyses every
  generic body from that definition-time information. If it ever cannot, it says so
  with a distinct error instead of passing quietly.

A few of these are breaking changes, and that is on purpose: Metel is still
experimental, and I would rather fix a spelling now than carry it.

## Next

The bridge is gone and I don't miss it. Treating a struct as a row you narrow,
instead of a value you convert into a row, put partial ownership *inside* the type
