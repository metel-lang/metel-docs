## The bridge that isn't there

In July the plan was a bridge. A struct would opt into a structural view with a
derive, expose its fields as a row, and take them back again:

```metel
#derive(ToRecord, FromRecord)
struct Handle { fd: i32, label: String }

let row: record { fd: i32, label: String } := handle.to_record();
let handle2 := Handle::from_record(row);
```

`ToRecord` to get the row out, `FromRecord` to put it back. The point was partial
consumption — letting the program say *this field is gone, these are still here* —
with `Rc` / `Arc` teardown as the case that needs it.

None of that got built, because building it made the bridge look redundant. A
struct doesn't need to be converted to a row. It is one.

## Every struct is a branded row

A struct declaration is two things: a row of fields, and a *brand* — a nominal
identity that says "this row is a `Handle`, and it is not interchangeable with
some other row that happens to have the same fields." The row and the brand come
apart. You can project a sub-row and keep the brand:

```metel
struct Handle { fd: i32, name: String }

let h := Handle { fd = 3, name = "log" };
let just_fd := h.{ fd };        // type: Handle.{ fd }
```

`Handle.{ fd }` is a *residual*: the `Handle` brand, narrowed to one field. It is
not an anonymous record — it still carries the identity, a parameter written
`Self.{ fd }` accepts it, and projecting it back to full width normalizes to plain
`Handle`.

## Partial moves narrow the type

The thing the bridge was for now just happens. Move a non-`Copy` field out of a
struct and the value's static type narrows to the residual:

```metel
var h := Handle { fd = 3, name = "log" };
let taken := h.name;         // h : Handle.{ fd }   — `name` moved out

read_fd(h.fd);               // fine, fd is still there
persist(h);                  // T0001: a partially-moved `Handle`
                             //        (now `Handle.{ fd }`) cannot be used
                             //        where the whole `Handle` is required
```

This is a type-checker fact, not a lint. After that line `h`'s type *is*
`Handle.{ fd }`. It is path-sensitive: each `if` / `match` arm forks from the state
before it and the arms rejoin afterward, so a move on one arm narrows `h` for the
code after the `match`, and a later arm never inherits an earlier arm's move.
`--move-check` is in on it too — using `h` at its narrowed type isn't flagged as a
partial-move violation, because at that type it isn't one.

A `Copy` field read by value doesn't narrow anything — copying `fd` out leaves `h`
a whole `Handle`. Only a move takes a field away.

If the binding owns its value, putting the field back widens the type again:

```metel
h.name := "reopened";        // h : Handle   again
```

No `FromRecord`, no constructor call. Ordinary field assignment already bypasses
constructor invariants; widening rides on that and adds nothing.

## The Rc case, and where it stops

The motivating example from the first post was `Rc` / `Arc`: when the last strong
reference goes, the payload has to be destroyed while the allocation and the
counts stay live until the weak references are gone too. Inside a function that
owns the box, that decomposition is exactly the narrowing above:

```metel
struct RcBox<T> {
    strong: u64,
    weak:   u64,
    value:  T,
}

fun into_value<T>(box: RcBox<T>) -> T {
    let v := box.value;      // box : RcBox<T>.{ strong, weak }
    log_counts(box.strong, box.weak);
    v
}
```

`box.value` moves out; `box` is now `RcBox<T>.{ strong, weak }`, and the counters
stay readable and correctly typed for the rest of the body.

Two pieces of the real thing aren't here yet, and it's worth being precise about
which:

- **Decomposition through a `&var`.** `Rc::drop_slow` doesn't own the box — it
  works through `&mut self`. Metel rejects moving a field out of a reference at
  all: a reference grants access, never ownership. The narrowed receiver that
  would make it sound — projecting `&var self` down to `&var Self.{ strong, weak }`
  — is RFC-0137 §5, scheduled for v0.14.0. Until then, field-sensitive ownership
  *through a borrow* is still an open edge.
- **`Drop` dispatch on a residual.** A type with a `Drop` impl currently can't be
  partially moved at all, for the same missing-narrowed-receiver reason. So the
  pattern works for a box you tear down explicitly, not one with a destructor.

## "I only touch these fields", generically

The other half of the first post's motivation was the generic version — a function
that wants *any value with an `x` and a `y`* without naming a type. That's a row
bound:

```metel
fun magnitude_sq<record T: { x: f64, y: f64, .. }>(p: T) -> f64 {
    p.x * p.x + p.y * p.y
}
```

`..` makes the row open: *at least* these fields. Drop it and the bound is closed —
exactly these, nothing else. A field can pin the label without a type
(`{ x, y: f64, .. }`), and a bound can be negative per field: `!{ token }` accepts
any record with no `token` label at all, `!{ x: f64 }` accepts one whose `x` is
some other type.

Row bounds are satisfied by anonymous records only. A struct never satisfies one.
The brand is the whole reason a struct is nominal; erasing it silently to slot into
a structural bound would defeat the point. Struct data flows through row-bounded
code by handing over the fields explicitly — there's no implicit struct-to-row
coercion, by design.

This is the ground Niko Matsakis's [view types][vt] sketch is on: letting a
function or a borrow see a subset of a value's fields so a partial move or a
disjoint borrow type-checks. Metel reaches it through an explicit structural type
plus a brand, rather than by annotating references.

[vt]: https://smallcultfollowing.com/babysteps/blog/2021/11/05/view-types/

## Records with no brand to begin with

Data that has a shape but no identity is its own type: `{ x = 1.0, y = 2.0 }` as a
value, `{ x: f64, y: f64 }` as a type.

- **Exact.** `{ x: i64, y: i64 }` and `{ y: i64, x: i64 }` are the same type;
  `{ x: i64 }` and `{ x: i64, y: i64 }` are not, and neither is a subtype of the
  other. There is no width subtyping — a record with an extra field is a different
  type, not a compatible one.
- **No behaviour.** No methods, no aspect impls, no `Drop`. A record composes
  `Send` / `Sync` from its fields and carries nothing else. If you want behaviour
  attached, you want a brand, which means a struct.
- **They narrow the same way.** `let a := r.left;` leaves `r : { right: i64 }`.
  The only difference from a struct residual: there's no brand on what's left, so a
  stale whole-value use is an ordinary shape mismatch rather than a
  "partially-moved" diagnostic — same `T0001`, plainer wording.
- **`{ x }` in statement position is still a block.** Where it's ambiguous,
  parenthesize the record: `({ x = e })`. The diagnostic tells you so at the point
  of use.

## Matching

Struct patterns match named structs now — they didn't before v0.13, despite
turning up in spec examples that were never actually accepted:

```metel
match (token) {
    Token { kind, span, .. } => handle(kind, span),
    _ => skip(),
}
```

Bare field bindings only for the moment — `Token { kind: Ident, .. }`, a
sub-pattern on a field, isn't in yet. The trailing `..` is required unless the
pattern names every field, and naming a private field from outside the declaring
module is rejected the same as it is in construction.

## Where it lands

Scoring the first post's "closest thing to an open problem" against what's built:

| | status |
| --- | --- |
| owned decomposition | done — partial move narrows to a residual, reassignment widens it back |
| explicit projection | done — `v.{ a, b }` is a first-class sub-row that keeps the brand |
| generic "only these fields" | done for records, via row bounds |
| decomposition through a `&var` | **not done** — needs the narrowed receiver (RFC-0137 §5, v0.14.0) |

Still ahead beyond that: named records (a record shape *with* a brand and no
positional constructor), row-polymorphism past what the bounds can currently say,
and the unified identity mechanism that a brand is one case of — RFC-0159 is in
review for it. Parenthesized record and tuple literals (RFC-0151) are next now that
the pipe-closure switch freed up `(...)`.

The bridge is gone and I don't miss it. Treating a struct as a row you narrow,
instead of a value you convert into a row, put partial ownership *inside* the type
checker instead of on top of it as a library.
