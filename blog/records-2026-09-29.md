The [first post](/blog/introducing-metel) said records would get their own writeup
once the design was further along. It is — and the design changed on the way. So
this is both the promised post and a correction to it.

<!--truncate-->

## The bridge that isn't there

In July the plan was a bridge. A struct would opt into a structural view with a derive,
expose its fields as a row, and take them back again:

<!-- doc-example: skip reason="the abandoned July design, not valid Metel" -->
```metel
#derive(ToRecord, FromRecord)
struct Handle { fd: i32, label: String }

let row := handle.to_record();           // struct -> row
let handle2 := Handle::from_record(row); // row -> struct
```

The point was partial consumption: let the program say *this field is gone, these are
still here*, with `Rc` / `Arc` teardown as the case that needs it. None of it got built,
because building it made the bridge look redundant. A struct doesn't need converting to a
row. It is one.

## Every struct is a branded row

A struct declaration is two things: a row of fields, and a *brand*, a nominal identity
that says "this is a `Handle`, not any other row that happens to have the same fields."
The two come apart. You can project a sub-row and keep the brand:

```metel
struct Handle { fd: i32, name: String }

fun main() {
    let h := Handle { fd = 3, name = "log" };
    let just_fd: Handle.{ fd } := h.{ fd };   // brand kept, one field left
    assert(just_fd.fd == 3);
}
```

`Handle.{ fd }` is a *residual*: the `Handle` brand narrowed to one field. It isn't an
anonymous record. A parameter written `Self.{ fd }` accepts it, and projecting it back to
full width gives plain `Handle` again.

## Partial moves narrow the type

What the bridge was for now just happens. Move a non-`Copy` field out of a struct and the
value's static type narrows to the residual:

```metel
struct Handle { fd: i32, name: String }

fun read_fd(fd: i32) -> i32 { fd }

fun main() {
    var h := Handle { fd = 3, name = "log" };
    let taken := h.name;         // `name` moved out: h : Handle.{ fd }
    assert(read_fd(h.fd) == 3);  // fd is still there, so this is fine
    h.name := "reopened";        // put it back: h : Handle again
    assert(h.name == "reopened");
}
```

This is a type-checker fact, not a lint. After the move, `h` *is* a `Handle.{ fd }`, and
using it where a whole `Handle` is required is an error:

<!-- doc-example: expect-fail reason="using a partially-moved value as a whole is the point" -->
```metel
struct Handle { fd: i32, name: String }

fun persist(h: Handle) -> i32 { h.fd }

fun main() {
    var h := Handle { fd = 3, name = "log" };
    let taken := h.name;   // h : Handle.{ fd }
    persist(h);            // T0001: `Handle.{ fd }` cannot be used where the
                           //        whole `Handle` is required
}
```

The narrowing is path-sensitive: each `if` / `match` arm forks from the state before it,
and the arms rejoin afterward. Reading a `Copy` field narrows nothing; only a move takes a
field away. Assigning it back widens the type again, with no `FromRecord`, because field
assignment already bypasses constructor invariants. Move the *last* non-`Copy` field and
what is left is the empty residual `Token.{}`, which keeps the brand and widens on
reassignment.

## The Rc case

The motivating example from the first post was `Rc` / `Arc`: when the last strong
reference goes, the payload is destroyed while the allocation and counts stay live for the
weak references. Inside a function that owns the box, that is exactly the narrowing above:

```metel
struct RcBox<T> { strong: i64, weak: i64, value: T }

fun log_counts(strong: i64, weak: i64) -> i64 { strong + weak }

fun into_value<T>(box: RcBox<T>) -> T {
    let v := box.value;                  // box : RcBox<T>.{ strong, weak }
    log_counts(box.strong, box.weak);    // the counters are still readable
    v
}

fun main() {
    assert(into_value(RcBox { strong = 1, weak = 2, value = 7 }) == 7);
}
```

That covers a box you tear down yourself. Letting the standard `Rc` do the same from its
own `drop` needs one more piece: a method that borrows only part of `self`, written as a
narrowed receiver `&var Self.{ strong, weak }`. It is specified in RFC-0137 §5 and
scheduled for v0.16.0, and it unlocks two things together: moving a field out through a
`&var`, and a `drop` that declares which fields it needs. Until then, a type with a `Drop`
impl can't be partially moved under `--move-check`.

## "I only touch these fields", generically

The other half of the first post's motivation was the generic version: a function that
wants *any value with an `x` and a `y`* without naming a type. That's a row bound:

```metel
fun magnitude_sq(p: { x: f64, y: f64, .. }) -> f64 {
    p.x * p.x + p.y * p.y
}

fun main() {
    assert(magnitude_sq({ x = 3.0, y = 4.0 }) == 25.0);            // exactly x, y
    assert(magnitude_sq({ x = 3.0, y = 4.0, z = 9.0 }) == 25.0);   // extra z is fine
}
```

`..` makes the row open: *at least* these fields. Drop it and the bound is closed: exactly
these, nothing else. To name the argument's type, say to hand the same value back, declare
it: `fun reset<record T: { x: f64, .. }>(p: T) -> T`. A bound can also be negative:
`!{ token }` accepts any record with no `token` label.

A plain struct never satisfies a row bound. The brand is the reason a struct is nominal,
and erasing it silently to fit a structural bound would defeat the point. Struct data
flows through row-bounded code by handing over the fields explicitly; there is no implicit
struct-to-row coercion.

## Prior art: Niko's view types

Everything so far has a close relative that I should name properly: Niko Matsakis's series
on view types for Rust: [View types for Rust][vt1] (2021), [View types redux and abstract
fields][vt2] (2025), [Maximally minimal view types][vt3] (March 2026) and its
[follow-up][vt4]. The 2021 post states the problem best: a function that touches one field
shouldn't have to give up the whole value. His answer is a view type, `Manifest.{ statistics }`
in the latest spelling: the struct, with only some fields accessible. Metel's residual
`Handle.{ fd }` is the same idea, down to his 2025 example, where two fields move into a
view and the third stays usable:

<!-- doc-example: skip reason="Rust-syntax sketch from the 2025 post, shown for comparison" -->
```text
let t: {a, c} Strings = {a, c} s;   // s.b stays usable, t.b is an error
```

The same program in Metel:

```metel
struct Strings { a: String, b: String, c: String }

fun main() {
    let s := Strings { a = "a".to_string(), b = "b".to_string(), c = "c".to_string() };
    let t: Strings.{ a, c } := s.{ a, c };   // moves a and c out of s
    assert(s.b == "b");                      // the rest of s is still usable
    assert(t.a == "a" && t.c == "c");        // t.b would be an error
}
```

Where I differ, or am behind him:

- **Borrows vs moves.** His call site builds the view (`&mut *self.{ statistics }`) and
  the borrow checker records a loan per field. Metel can't lend a sub-row of an owned
  value, and a method can't declare a narrowed `self`. Partial borrows only mean something
  with a borrow checker to enforce them, and Metel's (RFC-0122) is still a design, so I
  built the move half first.
- **A projection is a move.** `h.{ name }` moves the field out and keeps the brand, so
  `&h.{ name }` on a non-`Copy` field is an error for now.
- **Generics and privacy.** He defers inferring field sets; Metel took row polymorphism
  early (the open rows below). He proposes abstract fields so a signature needn't name
  private ones; I have no counterpart, and a `record` publishes every field.

I don't want to present any of the overlap as independent invention. The problem, the
view-type framing, the partial-move example and the dot spelling are in his posts, and all
predate Metel's first commit (March 30, 2026). If you came here for the idea itself, read
his series first.

[vt1]: https://smallcultfollowing.com/babysteps/blog/2021/11/05/view-types/
[vt2]: https://smallcultfollowing.com/babysteps/blog/2025/02/25/view-types-redux/
[vt3]: https://smallcultfollowing.com/babysteps/blog/2026/03/21/view-types-max-min/
[vt4]: https://smallcultfollowing.com/babysteps/blog/2026/03/22/max-min-view-types-followup/

## Records with no brand to begin with

Data that has a shape but no identity is its own type: `{ x = 1.0, y = 2.0 }` as a value,
`{ x: f64, y: f64 }` as a type.

- **Exact.** Field order doesn't matter: `{ x: i64, y: i64 }` and `{ y: i64, x: i64 }` are
  the same type. `{ x: i64 }` and `{ x: i64, y: i64 }` are not, and neither is a subtype of
  the other. There is no width subtyping.
- **No inherent behaviour.** No methods and no `Drop`. An anonymous record gets `Copy`,
  `Display`, `Clone`, `Send` and `Sync` from its fields, and an aspect can be implemented
  for a record shape. If you want methods attached, you want a brand.
- **They narrow the same way.** `let a := r.left;` leaves `r : { right: i64 }`. With no
  brand on what's left, a stale whole-value use is an ordinary shape mismatch (`T0001`)
  rather than a "partially-moved" diagnostic.
- **`{ x }` in statement position is still a block.** Where it's ambiguous, parenthesize:
  `({ x = e })`.

## `record`: the brand you can see through

That leaves a gap. A struct has a brand but its row is invisible to row bounds. An
anonymous record has a visible row but no brand. v0.14.0 fills it with a named record,
written `record` instead of `struct`:

```metel
record Point { x: f64, y: f64 }

fun magnitude_sq(p: { x: f64, y: f64, .. }) -> f64 {
    p.x * p.x + p.y * p.y
}

fun main() {
    assert(magnitude_sq(Point { x = 3.0, y = 4.0 }) == 25.0);   // a record passes
}
```

A `record X { … }` is a `struct X { … }` in every respect (name, brand, construction,
field access, coherence) except one: its declared row is *structurally visible*. It
satisfies row bounds and matches row-conditional impls. The same code with `struct` fails:

<!-- doc-example: expect-fail reason="a plain struct never satisfies a row bound — the point" -->
```metel
struct Point { x: f64, y: f64 }

fun magnitude_sq(p: { x: f64, y: f64, .. }) -> f64 {
    p.x * p.x + p.y * p.y
}

fun main() {
    magnitude_sq(Point { x = 3.0, y = 4.0 });
    // T0012: `Point` is a struct, but a struct never satisfies a row bound;
    //        declare it as a `record` instead
}
```

Switching from `struct` to `record` is additive: name, brand, generic parameters and impls
are unchanged, and the type newly passes row bounds. The cost is that every field becomes
public, because publishing the row is what lets other code match on it. A record field
can't be private; writing `public` on one is a syntax error that points you at `struct`.

A record also gets field-wise built-ins: `Copy`, `Display` and `Clone` derive from the
fields (`Display` prints in label order and keeps the record's name). A struct doesn't
acquire any of them just because its fields have them. Field-wise `Eq`, `Hash` and `Ord`
are deferred.

## Open rows

An open row in a bound says *at least these fields*. v0.14.0 lets you name the rest:
`..R` is a row tail, `row R` declares a row parameter, and a function can promise
something about its tail without knowing what is in it. The case that shows what this buys
is a typestate: strip a field off a record and put it back, with the compiler tracking
what is left.

```metel
// `Rest` is whatever the argument has besides `token`; the call derives it.
fun strip<row Rest>(d: { token: String, ..Rest }) -> { ..Rest } {
    let { token: _, ..rest } := d;   // `..rest` binds everything not named
    rest
}

// `!{ token }` guarantees the label being added isn't already there.
fun add_token<row R: !{ token }>(d: { ..R }) -> { token: String, ..R } {
    { token = "secret", ..d }        // spread the rest of `d` after `token`
}

fun main() {
    let redacted := strip({ token = "t", user = 3 });   // { user: i64 }
    assert(redacted.user == 3);
    let signed := add_token(redacted);                  // { token: String, user: i64 }
    assert(signed.user == 3);
}
```

Three things are new there. A row *tail* beside other fields, `{ token: String, ..Rest }`,
says what the argument is made of. A *remainder pattern*, `..rest`, binds everything the
other patterns didn't take, as an owned row. A *spread*, `{ token = "secret", ..d }`,
builds a record from one owned row, with spread labels unable to overwrite explicit
fields. When the row belongs to a named type and there is nowhere to write the tail inline,
a row *equation* (`where R = { auth: String, ..Rest }`) says the same thing from outside.

Throwing fields away is the part that needs a guard. Passing a record by value to an
open-row parameter *forgets* whatever the parameter doesn't name, and a forgotten field has
to be `Copy`, because otherwise nothing would own it afterwards:

```metel
fun get_x<row R>(p: { x: f64, ..R }) -> f64 { p.x }

fun main() {
    let r := { x = 1.0, count = 7 };   // `count` is Copy: forgetting it is fine
    assert(get_x(r) == 1.0);
}
```

<!-- doc-example: expect-fail reason="forgetting a non-Copy field is the point" -->
```metel
fun get_x<row R>(p: { x: f64, ..R }) -> f64 { p.x }

fun main() {
    let r := { x = 1.0, label = "gone".to_string() };
    let _ := get_x(r);
    // T0033: passing `{ label: String, x: f64 }` by value to an open row parameter
    //        forgets field `label` of type `String`, which is not `Copy`
}
```

A generic function can't see the fields of its own row, so it has to say what it needs.
`where all R: Copy` constrains every field of the row, open tail included, and can be
forwarded through generic calls:

```metel
fun copy_twice<row R>(value: { ..R }) -> ({ ..R }, { ..R })
where all R: Copy {          // without this, the second use of `value` is a use after move
    (value, value)
}

fun main() {
    let pair := copy_twice({ count = 5, label = 'x' });
    assert(pair.0.count + pair.1.count == 10);
}
```

## Two builders

Open rows make builders whose missing steps are compile errors. The first keeps the
settings in an anonymous record. Each step adds one label, and `!{ label }` stops it being
added twice:

```metel
fun url<row R: !{ url }>(b: { ..R }, u: String) -> { url: String, ..R } {
    { url = u, ..b }
}

fun header<row R: !{ header }>(b: { ..R }, h: String) -> { header: String, ..R } {
    { header = h, ..b }
}

fun retries<row R: !{ retries }>(b: { ..R }, n: i64) -> { retries: i64, ..R } {
    { retries = n, ..b }
}

// `send` needs a url and a header; any other setting rides along in `..R`.
fun send<row R>(b: { url: String, header: String, ..R }) -> String {
    b.url + " via " + b.header
}

fun main() {
    let req := retries(header(url({}, "a.com"), "x"), 3);   // order doesn't matter
    assert(send(req) == "a.com via x");
    assert(req.retries == 3);
}
```

Skip a required step and `send` doesn't compile:

<!-- doc-example: expect-fail reason="a builder missing a required step is the point" -->
```metel
fun url<row R: !{ url }>(b: { ..R }, u: String) -> { url: String, ..R } {
    { url = u, ..b }
}

fun send<row R>(b: { url: String, header: String, ..R }) -> String {
    b.url + " via " + b.header
}

fun main() {
    let req := url({}, "a.com");   // no header
    send(req);
    // T0012: row bound `{ header: String, url: String, .. }` requires label
    //        `header`, but the record has: url
}
```

The second keeps the builder as a named `record`, so it has an identity as well as a row.
A row equation takes a field out of its `data` and leaves everything else typed as it was:

```metel
record Builder<row R> { name: String, data: { ..R } }

// Take `auth` out of the data; the rest keeps its type.
fun redact<row R, row Rest>(b: Builder<..R>) -> Builder<..Rest>
where R = { auth: String, ..Rest } {
    let { name, data } := b;
    let { auth: _, ..rest } := data;
    Builder { name = name, data = rest }
}

// Works on any builder, whatever else it carries.
fun label<row R>(b: Builder<..R>) -> String {
    "request " + b.name
}

fun main() {
    let b := Builder { name = "login", data = { auth = "tok", retries = 3, verbose = true } };
    let safe := redact(b);               // data : { retries, verbose }
    assert(label(safe) == "request login");
    assert(safe.data.retries == 3);
}
```

## Matching

Struct patterns match named structs, and record patterns bind a remainder:

```metel
struct Token { kind: i64, span: i64, text: String }

fun handle(kind: i64, span: i64) -> i64 { kind + span }

fun main() {
    let token := Token { kind = 1, span = 2, text = "t" };
    let r := match (token) {
        Token { kind, span, .. } => handle(kind, span),   // `..` skips `text`
    };
    assert(r == 3);

    let { id, ..rest } := { id = 7, name = "a", age = 3 };   // rest : { name, age }
    assert(id == 7 && rest.age == 3);
}
```

One difference from the narrowing above is worth knowing before you hit it. Moving fields
out one at a time keeps the brand; a rest pattern does not. `..rest` binds a new anonymous
record, and the nominal brand stays behind:

```metel
record Token { value: String, id: i64 }

fun take(t: Token.{ id }) -> i64 { t.id }

fun main() {
    let a := Token { value = "x".to_string(), id = 1 };
    let v := a.value;                 // a : Token.{ id }, still a Token
    assert(take(a) == 1);

    let b := Token { value = "y".to_string(), id = 2 };
    let { value: _, ..rest } := b;    // rest : { id: i64 }, no brand
    assert(rest.id == 2);
}
```

Hand `rest` to something that wants `Token.{ id }` and the compiler says why, and tells you
to move the fields out one at a time to keep the brand. Methods and aspect impls on `rest`
are likewise those of an anonymous record, not `Token`'s.

Patterns take bare field bindings only for now: a sub-pattern on a field, as in
`Token { kind: 1, .. }`, isn't in yet. The trailing `..` is required unless the pattern
names every field, and naming a private field from outside its module is rejected, as it is
in construction.

## Where it lands

Scoring the first post's "closest thing to an open problem" against what's built:

| | status |
| --- | --- |
| owned decomposition | done: partial move narrows to a residual, reassignment widens it back |
| explicit projection | done: `v.{ a, b }` is a first-class sub-row that keeps the brand |
| generic "only these fields" | done: row bounds, open row parameters, equations, field-wise bounds |
| a nominal type you can match structurally | done: `record` |
| decomposition through a `&var` | **specified, not built**: the narrowed `&var self` receiver (RFC-0137 §5, v0.16.0) |
| `Drop` dispatch on a residual | **specified, not built**: the same receiver, seen from the destructor |

The last two are one feature. What is still being settled is the receiver form itself, in
the self-view RFCs (0109 and 0147, both under review). Until it lands, the ban on partially
moving a type with a `Drop` impl stays in force under `--move-check`.

Still ahead: tuples as numeric-label rows (RFC-0151, a draft), field-wise `Eq`, `Hash` and
`Ord`, and the unified identity mechanism a brand is one case of (RFC-0159, in review). The
API I would want on top of this, and what it would let you build, is a separate post:
[What Rows Could Do Next](/blog/rows-next).

## Everything else since the first post

The first post went up on July 15; there have been six releases since (v0.10.0 through
v0.13.1) plus this one. The surface settled in v0.10.0 (`public`, `var`, `extend`,
`&var T`), enums and `Some`/`Ok`/`Err` became ordinary variants in v0.11.0, v0.12.0 brought
anonymous records and the opt-in `--move-check`, and v0.13.0 was the closure cluster plus
the partial-move narrowing in this post. This release adds named records, open rows, `[T]`
and `[T; N]` array types, and generic bodies checked against their declared bounds. The
[changelog](/docs/release-notes/changelog) has the long version. Some of these are breaking
changes, on purpose: Metel is still experimental, and I would rather fix a spelling now
than carry it.
