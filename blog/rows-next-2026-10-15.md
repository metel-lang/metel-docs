The [records post](/blog/records) is about what is built: a struct is a row, partial
moves narrow its type, and open rows let a function say "I only touch these fields". This
one is about what I would want on top of that, and what it would make possible. Nothing in
it exists unless a block says it runs, and the blocks that do run are labelled as such.

<!--truncate-->

## What an ergonomic row API could look like

The [records post](/blog/records) is the mechanism. What I haven't built is the layer you
would want to write against. To see how much that matters I wrote the small programs a
person reaches for: rename a field, add one, drop one, merge two records. Most of them work
today, one function per field:

<!-- doc-example: skip reason="dated post, kept as published: written when the `row` kind existed (RFC-0186 replaced it with `record R`)" -->
```metel
fun with_token<row R: !{ token }>(d: { ..R }, t: String) -> { token: String, ..R } {
    { token = t, ..d }
}

fun with_alloc<row R: !{ alloc }>(d: { ..R }, a: i64) -> { alloc: i64, ..R } {
    { alloc = a, ..d }
}

fun main() {
    let r := with_alloc(with_token({ n = 1 }, "t".to_string()), 5);
    assert(r.alloc == 5);
}
```

Those two functions differ only in a label, and I can't write the operation once. That is
the pattern in every program I tried, so the rest of this section is what it would take to
close it. None of it exists; each item says where its design lives and how settled it is.

**Rename and add are the same hole.** The thing missing is a *label* as a generic
parameter, so `token` and `alloc` can be arguments the way a type is:

<!-- doc-example: skip reason="design sketch (RFC-0175, a draft); label parameters do not exist" -->
```metel
fun insert<label L, T, row R: !{ L }>(r: { ..R }, .L, v: T) -> { L: T, ..R }
fun delete<label L, T, row R>(r: { L: T, ..R }, .L) -> { ..R }
fun rename<label From, label To, T, row R: !{ To }>(r: { From: T, ..R }, .From, .To) -> { To: T, ..R }
```

The `.L` in a parameter list is a guess at how a label becomes an argument: the definition
mirrors the call, where a label is written `.token`. RFC-0175 writes the label as a string
in a turbofish, `get_field::<"token", _, Token>`, and calls that "only notation". I prefer an
argument: a turbofish is positional, so every other generic parameter needs a `_`, and a
string looks like a value you could compute at run time, which a label never is. A leading
`.` is free in the grammar today.

RFC-0175 is that idea, still a draft. It already makes `value.[L]` a checked, erased access
against a known row rather than a run-time lookup. It doesn't spell the absence bound (`!{ L }`
above is my guess), and the ownership of a drained non-`Copy` field is left to the borrow
checker. If it lands, the functions above are a library, not a language feature, and since
`extend<row R> { ..R }` already exists they could read as methods:

<!-- doc-example: skip reason="design sketch; needs label parameters (RFC-0175) and generic methods on an open-row extend" -->
```metel
let session := request
    .insert(.token, token)
    .rename(.id, .user_id)
    .delete(.retries);
```

I'd rather that than a dozen built-in field operations, because a library can be wrong and
get fixed, and a built-in has to be right forever. PureScript's `Record.Builder` is the
closest working version I know of.

**Merge needs a fact the language can't state yet.** Combining two open records fails
outright, because there is one spread and one tail per record and nothing says the rows don't
share a label:

<!-- doc-example: skip reason="rejected today: a record literal takes one spread, and there is no disjointness constraint" -->
```metel
fun merge<row A, row B>(a: { ..A }, b: { ..B }) -> { ..A, ..B } where A # B {
    { ..a, ..b }
}
```

`A # B` is a *disjointness* constraint: the `!{ token }` bound generalised to two rows
lacking each other's labels. Ur/Web has it (`[r1 ~ r2]`) and types record concatenation with
it. I would want a clear error in the common case, and I don't have a draft for it yet.

**Doing something to every field is a different feature.** A `Display`, `Eq` or `Clone` for
any record has to walk the fields, and a label parameter doesn't help, since the labels aren't
known when you write the function. RFC-0174 proposes a compile-time `for` over a row's fields,
checked once against a symbolic field that has only the aspects `where all R: A` grants, then
unrolled when the row is known:

<!-- doc-example: skip reason="design sketch from RFC-0174 (under review); comptime for over a row does not exist" -->
```metel
extend<row R> { ..R }: Display where all R: Display {
    fun to_string(&self) -> String {
        var out := "{ ";
        comptime for field in fields(R) {
            out := out + field.name + " = " + self.[field.name].to_string() + ", ";
        }
        out + "}"
    }
}
```

That reads a record. Building one from per-field results (what `Clone` and `Default` need) is
an open question in the same RFC.

**Lending part of a value is the borrow checker's job.** It's the `&var` row of the
["Where it lands" table](/blog/records#where-it-lands), which is specified but not built. A projection moves, so there is no way to lend a sub-row of an
owned value without consuming it, and `&h.{ name }` is an error until there is a form that
borrows. RFC-0109 and RFC-0122 are where Metel's version would be settled, and I'd rather leave
it unsolved than guess ahead of the checker.

One more thing the experiment turned up was a bug. An inline tail like
`{ token: String, ..Rest }`, as in `strip` from the [records post](/blog/records), used to work
only when the rest of the record was `Copy`: with a `String` in the rest the compiler rejected
the call as forgetting a non-`Copy` field, even though `Rest` was handed back, while the
row-equation form worked. That is fixed in this release
([#1469](https://github.com/metel-lang/metel-core/issues/1469),
[#1471](https://github.com/metel-lang/metel-core/issues/1471)): a by-value open row takes the
whole record, so the two spellings agree.

If I had to order it: label parameters first, because most of the pain above
disappears with them; then iteration, then disjointness. The borrowing form comes with the
borrow checker.

## What you could build with it

The section above is about the API. This one is about why I would want it. Everything here
follows from a record being a row the type checker can see into. Some of it runs today and
most of it needs one of the pieces above; each item says which, and I have not run any block
marked as a sketch. The sketches use the draft syntax from the previous section: `label L`
(RFC-0175), `comptime for` over `fields(R)` (RFC-0174), and `A # B` for disjoint rows.

### A dependency container that is only a record

Wiring an application together usually means a container that looks things up at run time
and fails when you forgot to register something. A record whose labels are the dependencies
fails at compile time instead, because a function that needs a database asks for `db` and
nothing else:

<!-- doc-example: skip reason="dated post, kept as published: written when the `row` kind existed (RFC-0186 replaced it with `record R`)" -->
```metel
record Db { url: String }
record Logger { level: i64 }

fun with_db<row R: !{ db }>(env: { ..R }, d: Db) -> { db: Db, ..R } { { db = d, ..env } }
fun with_log<row R: !{ log }>(env: { ..R }, l: Logger) -> { log: Logger, ..R } { { log = l, ..env } }

fun connect<row R>(env: &{ db: Db, ..R }) -> String { env.db.url }

fun main() {
    let env := with_log(with_db({}, Db { url = "pg://prod" }), Logger { level = 2 });
    assert(connect(&env) == "pg://prod");
}
```

`connect` accepts any environment with a `db`, whatever else is in it, and calling it on one
without a `db` is a type error. `with_db` and `with_log` differ only in a label, which label
parameters would make one function: `env.insert(.db, db)`. The `!{ db }` bound already stops a
dependency being registered twice.

Passing a record of capabilities is the same pattern. A function that takes
`&{ net: Net, ..R }` can use the network and cannot name the file system, and running
something with fewer powers means passing fewer labels. Taking a capability away from a value
you already hold, without consuming it, is the borrowing question again.

### Middleware where order is checked

A request pipeline is the same trick with each stage adding or requiring keys. This runs
today:

<!-- doc-example: skip reason="dated post, kept as published: written when the `row` kind existed (RFC-0186 replaced it with `record R`)" -->
```metel
record User { name: String }

fun auth<row R: !{ user }>(req: { ..R }, name: String) -> { user: User, ..R } {
    { user = User { name = name }, ..req }
}

fun rate_limit<row R>(req: { user: User, ..R }) -> { user: User, ..R } { req }

fun handle<row R>(req: &{ user: User, ..R }) -> String { "hello " + req.user.name }

fun main() {
    let req := rate_limit(auth({ path = "/" }, "ada".to_string()));
    assert(handle(&req) == "hello ada");
    assert(req.path == "/");
}
```

`rate_limit` wants a user, so putting it before `auth` does not compile. The error today is
`cannot unify { path: String } with { user: User, ..?t }`, which says the right thing
unfriendly. `path` comes out the other end untouched, and a schema migration is the same
shape: `{ name: String, ..Rest }` to `{ full_name: String, ..Rest }`, leaving every field it
doesn't know alone.

### Two systems mutating the same value at once

This is the one I would most like to get to. If two rows are provably disjoint, two
functions can each hold a mutable borrow of their own part of one value at the same time:

<!-- doc-example: skip reason="design sketch; needs disjointness (no draft) and borrowing a sub-row, which does not exist yet" -->
```metel
fun physics(w: &var { pos: Vec2, vel: Vec2, .. }) { ... }
fun render(w: &{ pos: Vec2, sprite: Sprite, .. }) { ... }

fun step<row A, row B>(w: &var { ..A, ..B }, f: fn(&var { ..A }), g: fn(&var { ..B }))
where A # B {
    f(&var w.{ ..A });
    g(&var w.{ ..B });   // sound only because A # B
}
```

With a store of components laid out one column per label, each system declares the columns it
touches, and two systems can run in parallel exactly when their mutable sets are disjoint and
neither writes what the other reads. The compiler proves it, so there is no lock and no
run-time check; it is the fact Rust gets from `split_at_mut`, except that here the language
knows why the halves don't overlap. It needs the disjointness constraint, which has no draft,
and borrowing a sub-row of an owned value, which the ["Where it lands" table](/blog/records#where-it-lands) lists as specified but not
built. I would not promise this one until the borrow checker has settled it.

### Typed configuration, built in layers

Configuration arrives in layers, defaults then a file then the environment then the command
line, and the usual bug is a key nobody set. With rows the merged result has a type, so
"everything required was provided" is checkable:

<!-- doc-example: skip reason="design sketch; needs disjointness (A # B) and an explicit override form, neither of which exists" -->
```metel
let cfg := defaults.merge(file).merge(env);

fun start<row R>(cfg: &{ host: String, port: i64, ..R }) -> Server
```

`merge` refuses overlapping layers, which is right for sources that should never both set a
key. Layering with precedence needs an `over` where the second record wins for shared labels,
and I don't have a sketch of how to write that bound.

### A builder that knows what is missing

A struct literal is already named, order independent and checked for completeness:
`Config { host = "example.org", port = 8080, tls = true }` does not compile without `tls`. So a
builder earns its place only when a record is assembled across steps, branches or function
calls, with defaults, or with a check at the end. The interesting version is one where the
type remembers which fields are set, and `build()` does not exist until all of them are.

A first piece of that runs today. A wrapper carries its fields in a row, one function adds
a field, and `build` is defined only for a row that has `host`:

<!-- doc-example: skip reason="dated post, kept as published: written when the `row` kind existed (RFC-0186 replaced it with `record R`)" -->
```metel
record Req<row R> { data: { ..R } }

fun add_host<row R: !{ host }>(r: Req<..R>, h: String) {
    Req { data = { host = h, ..r.data } }
}

extend<row R: { host: String, .. }> Req<..R> {
    fun build(self) -> String { "GET " + self.data.host }
}

fun main() {
    let r := add_host(Req { data = {} }, "example.org");
    assert(r.build() == "GET example.org");
}
```

`add_host` has no return type written on purpose: the compiler works out that it returns a
`Req` whose row gained `host`, but that type can't be written down, as below. Calling `build`
before `add_host` is the error you want:

<!-- doc-example: expect-fail reason="build() needs a row with host, and an empty Req has none -- that is the point" -->
```metel
record Req<row R> { data: { ..R } }

extend<row R: { host: String, .. }> Req<..R> {
    fun build(self) -> String { "GET " + self.data.host }
}

fun main() {
    let r := Req { data = {} };
    let _ := r.build();
}
```

The message today is `no row-conditional implementation matches receiver` plus the missing
label, not "`build()` requires `host`".

Two filed gaps stop this from being a builder you would use. The type a setter returns can't
be written: a row argument in a type has to be a variable, so `Req<..{ host: String, ..R }>`
doesn't parse, and a `where S = { host: String, ..R }` equation leaves `S` opaque in the body.
A method without a written return type defaults to `()`, so a setter can't be a method
([#1473](https://github.com/metel-lang/metel-core/issues/1473)). And chaining two setters
loses the first, because the row is nested and field lookup sees only the outer layer
([#1472](https://github.com/metel-lang/metel-core/issues/1472)). When this builder is writable
and chains, those two fixes are enough.

What I want it to look like:

<!-- doc-example: skip reason="design sketch; needs #1472, #1473, label parameters (RFC-0175) and a way to name the row of a nominal type" -->
```metel
record Builder<T, row Have> { have: { ..Have } }

extend<T, row Have> Builder<T, ..Have> {
    fun set<label L, V>(self, .L, v: V) -> Builder<T, ..{ L: V, ..Have }>
    where Have: !{ L } { ... }
}

extend<T, row Have> Builder<T, ..Have> where Have = row_of(T) {
    fun build(self) -> T { ... }
}

let cfg: Config = Config.builder()
    .set(.host, "example.org")
    .set(.port, 8080)
    .build();        // error: build() requires `tls`
```

`row_of(T)` is a name I made up for the row of a nominal type's fields; I haven't looked at
how to spell it. The bound on `set` stops a field being set twice, and the bound on `build`
makes the error appear at the call. A `comptime for` over the fields could generate per-field
setters (`.host("example.org")`) instead of going through `set`.

Defaults and a final check (`.defaults({ port = 8080 })` before the setters, `.validate(...)`
before `build`) are what make this more than a literal. `build` would then return a `Result`
since validation can fail, so it isn't a drop-in upgrade, and I would keep the plain literal
for the common case.

### Writing it once for every record

Today `Display`, `Eq` and `Clone` for a record are built in or written per type. With a
compile-time `for` over the fields they are a library, and so is anything else that is "do this
to each field":

<!-- doc-example: skip reason="design sketch from RFC-0174 (under review); comptime for over a row does not exist" -->
```metel
fun diff<row R>(a: &{ ..R }, b: &{ ..R }) -> Patch<..R> where all R: Eq + Clone {
    var out := Patch.empty();
    comptime for field in fields(R) {
        if a.[field.name] != b.[field.name] {
            out.[field.name] := Some(b.[field.name].clone());
        }
    }
    out
}
```

The same loop gives field-wise `Default`, a per-field validator, a form description, and
serialisation without a derive macro. `Patch<..R>` is the awkward part: "`R` with every field
wrapped in `Option`" is a map over a row at the type level. RFC-0174 covers walking a row to
read it and names building one as an open question; a type-level map goes a step beyond that,
and I know of no draft for it.

### What each one is waiting on

| idea | runs today | needs |
| --- | --- | --- |
| dependency container | yes, one function per label | label parameters (RFC-0175) to write it once |
| ordered middleware | yes | nothing; friendlier errors would help |
| capabilities | yes | borrowing a sub-row, to narrow without consuming |
| field-wise derivations | no | comptime `for` (RFC-0174), plus a type-level row map for `Patch` |
| layered configuration | no | disjointness `A # B`, and an `over` form with precedence |
| builder that tracks missing fields | partly: `build` is gated on the row, the setter cannot be written | [#1473](https://github.com/metel-lang/metel-core/issues/1473), [#1472](https://github.com/metel-lang/metel-core/issues/1472), label parameters |
| parallel mutation | no | disjointness, and borrowing a sub-row (RFC-0109, RFC-0122) |

I would build them in that order, since each step needs less of what is missing than the
one after it.
