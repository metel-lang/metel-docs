The [records post](/blog/records) is about what is built: a struct is a row, partial
moves narrow its type, and open rows let a function say "I only touch these fields". This
one is about what I would want on top of that, and what it would make possible. Nothing in
it exists unless a block says it runs, and the blocks that do run are labelled as such.

<!--truncate-->

## What an ergonomic row API could look like

The [records post](/blog/records) is the mechanism. What I haven't built is the layer you
would actually want to write against, and I tried to find out how much that matters by writing the small
programs a person reaches for: rename a field, add one, drop one, merge two records. Most of
them work today, one function per field:

```metel
fun with_token<row R: !{ token }>(d: { ..R }, t: String) -> { token: String, ..R } {
    { token = t, ..d }
}

fun with_alloc<row R: !{ alloc }>(d: { ..R }, a: i64) -> { alloc: i64, ..R } {
    { alloc = a, ..d }
}

fun main() {
    let r := with_alloc(with_token({ n = 1 }, "t".to_string()), 5);
    assert(r.alloc == 5);
}
```

Those two functions differ only in a label. The operation, "add a field to whatever row you
were given", is the same, and I can't write it once. That is the pattern in every program I
tried, and I think it is the real gap, so the rest of this section is what it would take to
close it. None of it exists. Each item says where its design lives and how settled it is.

**Rename and add are the same hole.** The thing missing is a *label* as a generic
parameter, so `token` and `alloc` can be arguments the way a type is:

<!-- doc-example: skip reason="design sketch (RFC-0175, a draft); label parameters do not exist" -->
```metel
fun insert<label L, T, row R: !{ L }>(r: { ..R }, .L, v: T) -> { L: T, ..R }
fun delete<label L, T, row R>(r: { L: T, ..R }, .L) -> { ..R }
fun rename<label From, label To, T, row R: !{ To }>(r: { From: T, ..R }, .From, .To) -> { To: T, ..R }
```

The `.L` in a parameter list is a guess at how a label becomes an argument: the definition
mirrors the call, where a label is written `.token`. RFC-0175 doesn't fix this. It writes
the label as a string in a turbofish, `get_field::<"token", _, Token>`, and says that is
"only notation", with the real spelling left as an open question. I prefer an argument to a
turbofish for two reasons. A turbofish is positional, so every other generic parameter
needs a `_`. And a string looks like a value you could compute at run time, which a label
never is. A leading `.` is free in the grammar today, since `.` only appears after an
expression.

RFC-0175 is that idea, and it is still a draft. It already does the hard part, which is
making `value.[L]` a checked, erased access against a known row rather than a lookup at
run time. What it doesn't do is spell the absence bound (`!{ L }` above is my guess), and
the ownership of a drained non-`Copy` field is explicitly left to the borrow checker. If
that lands, the functions above are a library, not a language feature, and because
`extend<row R> { ..R }` already exists they could plausibly read as methods:

<!-- doc-example: skip reason="design sketch; needs label parameters (RFC-0175) and generic methods on an open-row extend" -->
```metel
let session := request
    .insert(.token, token)
    .rename(.id, .user_id)
    .delete(.retries);
```

I'd rather that than a dozen built-in field operations, because a library can be wrong
and get fixed, and a built-in has to be right forever. PureScript's `Record.Builder`
(`insert`, `modify`, `delete`, `rename`, `merge`) is the closest working version of this
that I know of, and Ur/Web's records are the other end of the same idea.

**Merge needs a fact the language can't state yet.** Combining two open records is the one
program that fails outright, because there is a single spread and a single tail per
record and nothing says the two rows don't share a label:

<!-- doc-example: skip reason="rejected today: a record literal takes one spread, and there is no disjointness constraint" -->
```metel
fun merge<row A, row B>(a: { ..A }, b: { ..B }) -> { ..A, ..B } where A # B {
    { ..a, ..b }
}
```

`A # B` is a *disjointness* constraint. It is the same kind of fact as the `!{ token }`
bound, which says one row lacks one label, generalised to two rows lacking each other's
labels. Ur/Web has this (`[r1 ~ r2]`), and it is how it types record concatenation. I
would want it with a clear error in the common case, and I don't have a draft for it yet.

**Doing something to every field is a different feature.** A `Display`, `Eq` or `Clone`
for *any* record has to walk the fields, and a label parameter doesn't help with that,
since the labels aren't known when you write the function. RFC-0174 is the proposal: a
compile-time `for` over a row's fields, checked once against a symbolic field that has only
the aspects `where all R: A` grants, then unrolled when the row is known.

<!-- doc-example: skip reason="design sketch from RFC-0174 (under review); comptime for over a row does not exist" -->
```metel
extend<row R> { ..R }: Display where all R: Display {
    fun to_string(&self) -> String {
        var out := "{ ";
        comptime for field in fields(R) {
            out := out + field.name + " = " + self.[field.name].to_string() + ", ";
        }
        out + "}"
    }
}
```

That reads a record. Building one from per-field results (what `Clone` and `Default`
need) is an open question in the same RFC, and I don't have a good answer to it yet.

**Lending part of a value is the borrow checker's job.** It's the row of the
["Where it lands" table](/blog/records#where-it-lands) that says not done. A projection moves, so there is no way to lend a sub-row of an owned
value without consuming it, and `&h.{ name }` is an error until there is a form that
borrows. Niko's view types are the map for that, and RFC-0109 and RFC-0122 are where
Metel's version would be settled. I'd rather leave it unsolved than guess ahead of the
checker.

One more thing the experiment turned up, and it's a bug, not a design question. An inline
tail like `{ token: String, ..Rest }`, as in `strip` from the [records post](/blog/records),
works only when the rest of that record is `Copy`. With a `String` in the rest, the
compiler rejects the call as forgetting a non-`Copy` field, even though `Rest` is named and
handed back. Writing the same signature with a row equation works. Those two spellings
should agree, and [#1469](https://github.com/metel-lang/metel-core/issues/1469) tracks it.
The quick fix I tried was the wrong one, so the design question behind it, whether a
by-value open row should take the whole record instead of narrowing it, is
[#1471](https://github.com/metel-lang/metel-core/issues/1471).

If I had to order it: fix that, then label parameters, because most of the pain above
disappears with them; then iteration, then disjointness. The borrowing form comes with the
borrow checker, whenever that is.

## What you could build with it

The section above is about the API. This one is about why I would want the API at all.
Everything here follows from a record being a row the type checker can see into, so none of
it needs a new kind of type. Some of it runs today, most of it needs one of the pieces
named above, and each item says which. I have not run any block marked as a sketch.

The syntax in the sketches is the draft syntax from the previous section: `label L`
parameters (RFC-0175), `comptime for` over `fields(R)` (RFC-0174), and `A # B` for
disjoint rows. Where a sketch needs something that has no draft at all, I say so.

### A dependency container that is only a record

Wiring an application together usually means a container that looks things up by name or
type at run time and fails when you forgot to register something. A record whose labels
are the dependencies does the same job and fails at compile time, because a function that
needs a database asks for `db` and nothing else:

```metel
record Db { url: String }
record Logger { level: i64 }

fun with_db<row R: !{ db }>(env: { ..R }, d: Db) -> { db: Db, ..R } { { db = d, ..env } }
fun with_log<row R: !{ log }>(env: { ..R }, l: Logger) -> { log: Logger, ..R } { { log = l, ..env } }

fun connect<row R>(env: &{ db: Db, ..R }) -> String { env.db.url }

fun main() {
    let env := with_log(with_db({}, Db { url = "pg://prod" }), Logger { level = 2 });
    assert(connect(&env) == "pg://prod");
}
```

`connect` accepts any environment that has a `db`, whatever else is in it, and calling it
on one without a `db` is a type error. The part I don't like is `with_db` and `with_log`,
which differ only in a label. With label parameters that is one function, and the call
reads as `env.insert(.db, db)`. The `!{ db }` bound already stops a dependency from
being registered twice.

### Middleware where order is checked

A request pipeline is the same trick with each stage adding or requiring keys. This runs
today:

```metel
record User { name: String }

fun auth<row R: !{ user }>(req: { ..R }, name: String) -> { user: User, ..R } {
    { user = User { name = name }, ..req }
}

fun rate_limit<row R>(req: { user: User, ..R }) -> { user: User, ..R } { req }

fun handle<row R>(req: &{ user: User, ..R }) -> String { "hello " + req.user.name }

fun main() {
    let req := rate_limit(auth({ path = "/" }, "ada".to_string()));
    assert(handle(&req) == "hello ada");
    assert(req.path == "/");
}
```

`rate_limit` wants a user, so putting it before `auth` does not compile. The error today
is `cannot unify { path: String } with { user: User, ..?t }`, which says the right thing in
an unfriendly way. Nothing in the stages knows about `path`, and it comes out the other end
untouched. A schema migration is the same shape, a function from
`{ name: String, ..Rest }` to `{ full_name: String, ..Rest }` that leaves every field it
doesn't know alone.

### Two systems mutating the same value at once

This is the one I would most like to get to. If two rows are provably disjoint, two
functions can each hold a mutable borrow of their own part of one value at the same time:

<!-- doc-example: skip reason="design sketch; needs disjointness (no draft) and borrowing a sub-row, which does not exist yet" -->
```metel
fun physics(w: &var { pos: Vec2, vel: Vec2, .. }) { ... }
fun render(w: &{ pos: Vec2, sprite: Sprite, .. }) { ... }

fun step<row A, row B>(w: &var { ..A, ..B }, f: fn(&var { ..A }), g: fn(&var { ..B }))
where A # B {
    f(&var w.{ ..A });
    g(&var w.{ ..B });   // sound only because A # B
}
```

Take a store of components laid out one column per label. Each system declares the
columns it touches, and a scheduler can run two systems in parallel exactly when their
mutable sets are disjoint and neither writes what the other reads. The compiler proves it,
so there is no lock and no run-time check. It is the same fact Rust gets from splitting a
slice with `split_at_mut`, except that here the language knows why the two halves don't
overlap.

It needs two things I don't have. One is the disjointness constraint, which has no draft.
The other is borrowing a sub-row of an owned value: a projection moves today, and the
["Where it lands" table](/blog/records#where-it-lands) lists decomposition through a
`&var` as not done. I would not promise this one
until the borrow checker has settled it.

### Typed configuration, built in layers

Configuration usually arrives in layers, defaults then a file then the environment then the
command line, and the usual bug is a key nobody set. With rows the result of merging has a
type, and "everything required was provided" is checkable:

<!-- doc-example: skip reason="design sketch; needs disjointness (A # B) and an explicit override form, neither of which exists" -->
```metel
fun merge<row A, row B>(a: { ..A }, b: { ..B }) -> { ..A, ..B } where A # B { { ..a, ..b } }

let cfg := defaults.merge(file).merge(env);

fun start<row R>(cfg: &{ host: String, port: i64, ..R }) -> Server
```

`merge` refuses overlapping layers, which is what you want for combining two sources that
should never both set a key. Layering with precedence is a different operation. It needs
an `over` that lets the second record win for the labels they share, and the result type
is the union with the right-hand type for each shared label. I don't have a sketch of how
to write that bound.

### A builder that knows what is missing

A struct literal in Metel is already named, order independent and checked for
completeness: `Config { host = "example.org", port = 8080, tls = true }` does not compile
without `tls`. So a builder only earns its place when a record is assembled across
steps, through branches or across function calls, with defaults, or with a check at the
end. For those cases the interesting version is one where the type remembers which fields
are set, and `build()` does not exist until all of them are.

A first piece of that runs today. A wrapper carries its fields in a row, one function adds
a field, and `build` is defined only for a row that has `host`:

```metel
record Req<row R> { data: { ..R } }

fun add_host<row R: !{ host }>(r: Req<..R>, h: String) {
    Req { data = { host = h, ..r.data } }
}

extend<row R: { host: String, .. }> Req<..R> {
    fun build(self) -> String { "GET " + self.data.host }
}

fun main() {
    let r := add_host(Req { data = {} }, "example.org");
    assert(r.build() == "GET example.org");
}
```

`add_host` has no return type written, and that is not an oversight. The compiler works out
that it returns a `Req` whose row gained `host`, but there is no way to write that type
down, which I come back to below. Calling `build` before `add_host` is the error you want:

<!-- doc-example: expect-fail reason="build() needs a row with host, and an empty Req has none -- that is the point" -->
```metel
record Req<row R> { data: { ..R } }

extend<row R: { host: String, .. }> Req<..R> {
    fun build(self) -> String { "GET " + self.data.host }
}

fun main() {
    let r := Req { data = {} };
    let _ := r.build();
}
```

The message today is `no row-conditional implementation matches receiver`, followed by
the label that is missing. It names the problem, though not as "`build()` requires `host`".

That is as far as it goes now. Two gaps stop it from being a builder you would use, and
both are filed. The first is that the type a setter returns cannot be written: a row
argument in a type has to be a variable, so `Req<..{ host: String, ..R }>` does not
parse, and a `where S = { host: String, ..R }` equation leaves `S` opaque inside the body.
A method without a written return type defaults to `()`, so a setter cannot be a method,
and `req.host("x").port(80)` cannot be written
([#1473](https://github.com/metel-lang/metel-core/issues/1473)). The second is that
chaining two setters loses the first one. The row after two additions is nested, and
looking a field up only sees the outer layer
([#1472](https://github.com/metel-lang/metel-core/issues/1472)). I would treat this builder
as the test for those two fixes: when it is writable and chains, they are enough.

What I want it to look like, with the label arguments from earlier:

<!-- doc-example: skip reason="design sketch; needs #1472, #1473, label parameters (RFC-0175) and a way to name the row of a nominal type" -->
```metel
record Builder<T, row Have> { have: { ..Have } }

extend<T, row Have> Builder<T, ..Have> {
    fun set<label L, V>(self, .L, v: V) -> Builder<T, ..{ L: V, ..Have }>
    where Have: !{ L } { ... }
}

extend<T, row Have> Builder<T, ..Have> where Have = row_of(T) {
    fun build(self) -> T { ... }
}

let cfg: Config = Config.builder()
    .set(.host, "example.org")
    .set(.port, 8080)
    .build();        // error: build() requires `tls`
```

`row_of(T)` is a name I made up for the row of a nominal type's fields. I expect the pieces
exist, since a struct is already a row the checker can see into, but I have not looked at
how to spell it. The bound on `set` stops a field being set twice, and the bound on
`build` is what makes the error appear at the call. With a `comptime for` over the fields
the per-field setters (`.host("example.org")`) could be generated instead of going through
`set`.

Defaults and a final check are what make this more than a literal:

<!-- doc-example: skip reason="design sketch; builds on the Builder above" -->
```metel
let cfg = Config.builder()
    .defaults({ port = 8080, tls = true })   // pre-filled; a later set overrides
    .set(.host, host)
    .validate(|c| c.port > 0)                // runs at build
    .build()?;                               // Result<Config, BuildError>
```

`build` returns a `Result` here, since validation can fail, so this is not a drop-in
upgrade over a literal. That is also why I would keep the plain literal for the common
case.

There is a second thing people call a record builder, from PureScript's `Record.Builder`:
a value that describes a record-to-record transformation, built from `insert`, `rename`
and `omit` and applied once. It makes a schema migration or a request shim a value you can
store and compose, and it can apply every step to one owned record in place, which is sound
here because `apply` consumes it. I would not add it. A plain function does the reuse job
and composes already, and the one-pass saving is worth building only if it is measured to
matter.

### Writing it once for every record

Today `Display`, `Eq` and `Clone` for a record are either built in or written per type.
With a compile-time `for` over the fields they are a library, and so is anything else that
is "do this to each field":

<!-- doc-example: skip reason="design sketch from RFC-0174 (under review); comptime for over a row does not exist" -->
```metel
fun diff<row R>(a: &{ ..R }, b: &{ ..R }) -> Patch<..R> where all R: Eq + Clone {
    var out := Patch.empty();
    comptime for field in fields(R) {
        if a.[field.name] != b.[field.name] {
            out.[field.name] := Some(b.[field.name].clone());
        }
    }
    out
}
```

The same loop gives field-wise `Default`, a validator that checks each field, a form
description, and serialisation without a derive macro. `Patch<..R>` is the awkward part:
it means "`R` with every field wrapped in `Option`", which is a map over a row at the type
level. RFC-0174 covers walking a row to read it, and it names building one as an open
question. A type-level map over a row is a further step beyond it, and I don't know of a
draft for that either.

### Tables and queries whose columns are checked

A table is a collection of rows, and a query is a function from one row type to another:

<!-- doc-example: skip reason="design sketch; needs label parameters, disjointness and row iteration, and none of the three exists" -->
```metel
let report := users
    .join(orders, on: .user_id)
    .select(.name, .total)
    .group_by(.name);
```

The compiler would check that `user_id` exists in both tables, that `name` and `total`
exist after the join, and that the two tables' other columns don't collide, which is
`A # B` again. This is the most speculative item here, because it wants all three of the
pieces above at once, and a query library has a great deal more to solve than its types.
I include it because it is the clearest case of rows being a schema.

### Capabilities in the signature

Passing a record of capabilities makes the signature say what a function can touch:

```metel
record Net { host: String }
record Fs { dir: String }

fun fetch<row R>(caps: &{ net: Net, ..R }) -> String { caps.net.host }

fun main() {
    let caps := { net = Net { host = "example.org" }, fs = Fs { dir = "/tmp" } };
    assert(fetch(&caps) == "example.org");
}
```

`fetch` can use the network and, because `fs` is only the tail it ignores, cannot name the
file system. To run something with fewer powers you pass a record with fewer labels. That
is the capability pattern with ordinary record typing doing the work, and it runs today.
What it can't do yet is take a capability away from a value you already hold without
consuming it, which is the same borrowing question as in the ECS item.

### What each one is waiting on

| idea | runs today | needs |
| --- | --- | --- |
| dependency container | yes, one function per label | label parameters (RFC-0175) to write it once |
| ordered middleware | yes | nothing; friendlier errors would help |
| capabilities | yes | borrowing a sub-row, to narrow without consuming |
| field-wise derivations | no | comptime `for` (RFC-0174), plus a type-level row map for `Patch` |
| layered configuration | no | disjointness `A # B`, and an `over` form with precedence |
| builder that tracks missing fields | partly: `build` is gated on the row, the setter cannot be written | [#1473](https://github.com/metel-lang/metel-core/issues/1473), [#1472](https://github.com/metel-lang/metel-core/issues/1472), label parameters |
| tables and queries | no | label parameters, disjointness and row iteration together |
| parallel mutation | no | disjointness, and borrowing a sub-row (RFC-0109, RFC-0122) |

I would build them in that order, since each step needs less of what is missing than the
one after it.
