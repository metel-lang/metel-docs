Metel 0.16.0 came out on 20 November. It is the release where the *surface* of the language got a
hard look: how a call is written, how a value is assigned, how a row label looks, what `Copy` means
on a declaration. Seven RFCs went in, most of them changing a spelling, and nearly all of those changes
are breaking. None of them is hard to migrate, and every one comes with a diagnostic that names the
new form.

<!--truncate-->

## Calls can name their arguments

A call can bind an argument by name, anywhere a call is written:

```metel
fun connect(host: String, port: i64, retries: i64) -> i64 { port + retries }

fun main() {
    let n := connect("db", port = 5432, retries = 3);
    assert(n == 5435);
}
```

It works for free functions, methods, associated functions, aspect methods and overloads (RFC-0223).
The rules are the ones you would guess. Positional arguments come first, each parameter is bound once,
and arguments evaluate in the order you wrote them, not the order of the parameters. A call through a
function value is positional only, because a function *value* has no parameter names to bind. Each way
to get this wrong has its own error code, from `T0039` (the name binds no parameter) to `T0041` (a
keyword in a call through a function value).

An impl method must now repeat the parameter names of the aspect it implements (`T0042`), since a
keyword argument has to mean the same thing whichever impl a call lands in. `From::from` takes its
argument as `value` for that reason.

## Assignment is a statement, and `:=` only introduces

`:=` used to be both "declare" and "assign". It now only introduces a name. Reassigning is `=`, and it
is a statement:

```metel
fun main() {
    var total := 0;
    total = total + 5;
    assert(total == 5);
}
```

Writing `total := total + 5;` where `total` already exists is a parse error. The other half of the
change is that an assignment is no longer an expression, so it cannot be an operand, an argument, a
condition or a block's tail value (RFC-0183). It also frees `=` to mean "bind to this name" in a call
(`f(x = 1)` is never an assignment), which is what the keyword arguments above rely on. One consequence
is easy to trip over: a block that ends in an assignment needs its `;`, so a closure that assigns is
written `|v| { total = v; }`.

## Labels start with a dot

In a record literal, a pattern, a type, a row bound or a projection, a label is written `.name`
(RFC-0221):

```metel
fun main() {
    let p := .{ .x = 1, .y = 2 };
    assert(p.x + p.y == 3);
}
```

The rule is: a name is dotted when it is a label of a row, and bare when it is a member that a nominal
type declares for itself. A struct's fields keep their bare names in its declaration; an anonymous
record and a projection list are views of a row, and there a label is written `.x`. Field selection is
unchanged: `p.x` is `p` followed by the label `.x`. Nothing about how records or rows behave changes,
only how a label is spelled.

The same release also marks the *value* itself: an anonymous record is written `.{ ... }`, with a
leading dot (RFC-0225), so it can never be mistaken for a block. A plain `{ .x = 1 }` is a parse error
that tells you to insert the `.`. The migration is a token-level rewrite, and the tool for it,
`label_migrate`, ships in `metel-frontend/examples`.

## Rows learn to say "not this"

A row bound can now say a label must be *absent*, with a `!` entry (RFC-0189):

```metel
fun log_in<record R: .{ .path: String, !.token, .. }>(req: R) -> String {
    req.path
}

fun main() {
    let r := .{ .path = "/home", .user = "ana" };
    assert(log_in(r) == "/home");
}
```

`log_in` accepts any record that has a `path` and has no `token`, whatever else it holds. An entry
comes in four forms: `.x` (a field `.x`, of any type), `.x: T` (a field of that type), `!.x` (no field
`.x`) and `!.x: T` (no `.x` of that type; an `.x` of another type is fine). The older whole-row negative
form stays, and is now defined as sugar for the entry form.

A record literal that spreads another record can also replace a field the spread is known to have
(RFC-0191): `.{ ..s, .a = 10 }`.

## `public` is now `pub`

The visibility keyword is `pub` (RFC-0218), which reverses an earlier rename to `public`. `public` is a
plain parse error now. Two reasons carried it. The keyword is written on every exported item (the
repository's own corpus had it on 514 lines across 248 files), so three letters add up. And it
composes with the new prefix keywords: `pub copy struct P` reads as one short prefix. No semantics
change: module-private by default, `pub` to expose, on functions, structs and their fields, records,
enums, aspects and type aliases.

`aspect`, `extends` and `public` are reserved words as well. The keyword matcher used to try a keyword
that is a prefix of another first, so those three had been parsing as identifiers.

## `Copy` is granted where the type is declared

This is the part of 0.16 with the most design in it, and the part that changes how a type reads.

`Copy` can no longer be granted by an `extend` block. A type says it is `Copy` where it is declared
(RFC-0206, RFC-0207):

```metel
copy struct Point { x: i64, y: i64 }          // shorthand for `derives Clone, Copy`
struct Pixel derives Clone, Copy { v: i64 }   // the same thing, spelled out

fun main() {
    let a := Point { x = 1, y = 2 };
    let b := a;                // copied, not moved
    assert(a.x + b.y == 3);
}
```

`extend Point: Copy;` is error `T0045`, with a fix-it that points at the declaration.

### Why it works this way

Three decisions fit together, and each one removes something that used to be a special case.

**A `Copy` type says so where it is declared.** Whether a value is copied or moved changes what every use of the type
means, so the one place a reader sees the type is where that fact belongs. It is also a plain consistency fix:
the compiler used to identify `Copy` by the string `"Copy"` at about 38 sites in the frontend, each one a special case
that a user's own aspect could not share. A conditional hand-written `Copy` impl can no longer exist. A generic type that
is `Copy` when its parameter is says so in its declaration.

**`Copy` is sealed: an implicit copy runs no user code.** The alternative was a hook that lets a type run code at each
implicit copy. That was explored and set aside, after three adversarial reviews found that running user code at an implicit
copy makes it observable *where the compiler inserts or removes* a copy. With a sealed copy nobody can tell, so the
compiler is free to turn a copy into a move at a value's last use. Rust's `Copy` and Swift's compiler-managed copy work
the same way. The door stays open: a user-writable hook can be added later as a separate, separately authorised mode
without breaking a program that is accepted today. A `Copy` type also cannot have a `Drop`, so a copy can never skip a
destructor (`T0015`).

**`Copy` requires `Clone`, and the `Clone` is the compiler's.** `Clone` is explicit duplication and may do anything a
function can. `Copy` is the implicit bit copy. For a `Copy` type the two have to agree, and Rust documents that they
should but cannot enforce it. Here a type that derives `Copy` derives `Clone` in its own entry (`derives Copy` alone is
`T0046`, and `copy struct` declares both), and the `Clone` of a `Copy` type is always the compiler's: it is the
representation copy. A hand-written `Clone` for a `Copy` type is an error (`T0015`). So `T: Copy` proves `T: Clone`, and
`x.clone()` on a `Copy` value is exactly the implicit copy. The two cannot disagree, because there is only one.

```metel
fun twice<T: Copy>(x: T) -> (T, T) { (x, x) }     // uses Copy
fun dup<T: Clone>(x: &T) -> T { x.clone() }        // a Copy type satisfies this bound too

fun main() {
    let (a, b) := twice(7);
    assert(a + b == 14);
    assert(dup(&5) == 5);
}
```

### The mechanism: properties, clauses and class keywords

Underneath, nothing is special-cased for `Copy`. It is described with a handful of general pieces (RFC-0212, RFC-0207).

An aspect declaration can carry **properties**, written before `aspect`:

| Property | Means | Who can use it |
|---|---|---|
| `declared` | granted only through a type's declaration, never by `extend` | anyone |
| `derivable` | the compiler has a derivation for it, so `derives A` is legal | std only, until comptime |
| `implicit` | a by-value use copies the representation instead of moving | std only |
| `auto` | reserved: granted structurally, with a negative impl as the opt-out | reserved |

`implicit` is the one property that is a language semantic and not a constraint, and `Copy` is the one aspect that has it.
Here is how std declares it, which is the whole mechanism in one line:

<!-- doc-example: skip reason="declared derivable implicit are std-only properties, and this is std's own declaration" -->
```metel
pub declared derivable implicit aspect Copy requires derived Clone, !Drop { /* .. */ }
```

`declared` is open to everyone. A method-less `declared` aspect is a marker: a promise, visible in the declaration, that
nothing checks:

```metel
declared aspect Validated;

struct Ticket: Validated { id: i64 }     // the colon list: facts the declaration claims

fun main() {
    let t := Ticket { id = 1 };
    assert(t.id == 1);
}
```

A declaration then has two clauses after its name and a class keyword before it:

- the **colon list** names `declared` markers the type claims (`struct Ticket: Validated`);
- the **`derives` clause** asks the compiler to write the impl of an aspect that has a derivation (`Clone`, `Copy`).
  Derivation is always explicit: a type with neither a `derives` entry nor an `extend` of an aspect does not have it;
- the **class keywords** `copy` and `linear` come before `struct` or `enum`. `copy` is `derives Clone, Copy`, and `linear`
  is reserved until linear types exist.

A derived impl and a written one for the same aspect overlap and are an error (`T0015`): a type customises an aspect by
writing the impl instead of deriving it.

**Super-aspects** state how aspects relate. `aspect Ord requires Eq` means a bound on `Ord` proves `Eq`, and an impl of
`Ord` needs a coherent impl of `Eq`. An entry marked `derived` is the interesting one: `Copy` is declared as requiring a
`derived Clone`, which is what turns "`Copy` needs `Clone`" from generation into a check. Nothing is generated from the
`Copy` entry, so each aspect keeps its own condition (`W<String>` can be `Clone` where it is not `Copy`), and the law
still holds by construction. The colon after an aspect's name and the mark `deriving` are parse errors that name the new
spelling.

### Generic types and the flow

For a generic type, `Copy` usually holds only when the parameters do. A derivation can say which, and that is its
**flow**:

```metel
struct Wrapper<T> derives Clone(T), Copy(T) { value: T }

fun main() {
    let w := Wrapper { value = 7 };
    let v := w;                  // Wrapper<i64> is Copy, since i64 is
    assert(w.value + v.value == 14);
}
```

`Wrapper<String>` is still `Clone` but not `Copy`. The flow replaces the earlier `via` clause, which is now a parse error
that names the new form (RFC-0227). Without an argument list the compiler computes the flow from the fields, and a `pub`
generic type has to state it, because the flow is part of its public interface.

### What the notation expands to

Each form is shorthand for a plain rewrite, applied in this order.

**1. The class keyword is a pair of entries.** `copy struct P { .. }` is `struct P derives Clone, Copy { .. }`. It is two
entries because `Copy` requires its own derived `Clone` entry, as above.

**2. An entry is an impl, bounded on its flow.** The compiler writes one ordinary impl per entry. It keeps the type's own
generics, and it puts a bound on exactly the parameters in the flow. The bound is the aspect being derived. So
`struct Wrapper<T> derives Clone(T), Copy(T) { value: T }` means, roughly:

<!-- doc-example: skip reason="an illustration of the expansion: a Copy impl cannot be written by hand (T0045)" -->
```metel
extend<T: Clone> Wrapper<T>: Clone {
    fun clone(&self) -> Wrapper<T> { Wrapper { value = self.value.clone() } }   // each field, in declaration order
}
extend<T: Copy> Wrapper<T>: Copy;                                               // the marker; the copy is the representation copy
```

`Clone` bounds its flow by `Clone` and `Copy` bounds its flow by `Copy`, which is why `Wrapper<String>` has the first impl
and not the second. A parameter outside the flow gets no bound at all: `derives Clone()` is `extend<T> W<T>: Clone` for every
`T`, and it is an error if a field holds a `T` by value. The compiler checks the stated flow against the fields. It must
contain every parameter a field depends on, with a fix-it that adds the missing one (`T0046`), and a flow larger than needed
is accepted. A reference field, like `r: &T`, depends on nothing.

**3. A computed flow is a stated flow the compiler fills in.** With no argument list, the compiler works out the smallest
set of parameters whose bound makes every field have the aspect, *separately for each aspect*, and then treats the entry as
if you had written that set:

<!-- doc-example: skip reason="0.16.0 computes the flow of a bare entry; 0.17.0 makes a bare entry unconditional, and this one an error" -->
```metel
copy struct Boxed<T> { value: T }     // 0.16.0: the compiler computes the flow, so this is derives Clone(T), Copy(T)
```

Written with the flow stated, the same type, next to one whose computed flow is empty:

```metel
struct Stated<T> derives Clone(T), Copy(T) { value: T }     // Copy when T is
copy struct View<T> { r: &T }                               // nothing needs `T: Copy`, so Copy for every T

fun main() {
    let n := Stated { value = 1 };
    let m := n;                       // Stated<i64> is Copy
    let s := "kept";
    let v := View { r = &s };
    let w := v;
    let u := v;                       // View<String> is Copy too: nothing in it needs `String: Copy`
    assert(n.value + m.value == 2);
    assert(s == "kept");
}
```

With a `String` the first type is no longer `Copy`, which a `T: Copy` bound sees:

<!-- doc-example: expect-fail reason="the second call is the error the example shows: Stated<String> is Clone but not Copy, so it does not satisfy the bound" -->
```metel
struct Stated<T> derives Clone(T), Copy(T) { value: T }

fun twice<T: Copy>(x: T) -> (T, T) { (x, x) }

fun main() {
    let fine := twice(Stated { value = 1 });
    let bad := twice(Stated { value = "text" });   // error: `Stated` does not implement `Copy`
}
```

Because every aspect computes its own set, a computed `copy` is two computations and not one shared list: the `Clone` flow
and the `Copy` flow can differ, as long as the `Clone` flow stays inside the `Copy` flow so that `T: Copy` still proves
`T: Clone`.

**In 0.17.0 the computed form gets its own spelling.** In 0.16.0 an entry with no argument list is the computed one. In
0.17.0 a bare entry will mean *no* condition on the parameters, and the computed flow is something you ask for (RFC-0244):

| Written | 0.16.0 | 0.17.0 | Expands to |
|---|---|---|---|
| `copy struct Boxed<T> { value: T }` | computed | an error: `value: T` needs `T: Copy` | |
| `copy? struct Boxed<T> { value: T }` | not available | computed | `derives Clone(..), Copy(..)`, so `derives Clone(T), Copy(T)` |
| `copy struct Id<T> { n: i64 }` | computed, which is empty | no condition | `derives Clone, Copy`, so `derives Clone(), Copy()` |
| `derives Clone(T), Copy(T)` | stated | stated | the two impls above |

`copy?` is the one-word form of `derives Clone(..), Copy(..)`, where `(..)` is "the rest of what the fields need".
The reason is that conditionality becomes visible at the declaration, the way `Copy`-ness already is. A type that is `Copy`
for every argument says so by being written `copy`, and a type that is `Copy` only for some says so by being written
`copy?`. That is not part of this release.

### Where this is going: derivations as comptime functions

Everything above is how the compiler does it today: `Clone` and `Copy` are the only derivable aspects, and their
derivations are built in. The design that is under review (RFC-0238, RFC-0246) makes a derivation an ordinary comptime
function that any aspect can provide, and the compiler's own are written the same way. None of this exists yet, and parts of
it are still open, so read the rest of this section as a sketch.

A `derives` clause is a call. An aspect becomes derivable by implementing the std aspect `Derivable` for itself, and the clause's
arguments are the `Args` of that impl. Std's `Clone` and `Copy` would be:

<!-- doc-example: skip reason="a design under review (RFC-0238): Derivable and comptime fun do not exist yet" -->
```metel
extend Clone: Derivable {
    type Args = Flow;                       // a flow of any width
    comptime fun derive(Target: type, args: Self::Args) -> Decl { field_wise(Clone, Target, args) }
}
extend Copy: Derivable {
    type Args = Flow;
    comptime fun derive(Target: type, args: Self::Args) -> Decl { field_wise(Copy, Target, args) }
}
```

`field_wise` is a std combinator that returns one declaration: an impl of the aspect for `Target`, with a bound on each
parameter in the flow, whose methods work field by field. Until comptime can run it, the compiler provides the same impls
natively. For a clause, the compiler then does four things: it finds the `Derivable` impl, builds the arguments as a call
row (`derives Clone(T)` is `.{ .0 = T }`, where `T` is one of the declaration's own type parameters), checks the row
against `Args`, and runs `derive` at compile time. The declaration it returns is added as an ordinary impl, checked for
coherence like any written one. In effect:

<!-- doc-example: skip reason="an illustration of what the compiler would do; emit is not available to programs" -->
```metel
struct Wrapper<T> derives Clone(T), Copy(T) { value: T }

// is, in effect:
//   emit Clone::derive(Wrapper, .{ .0 = T });   // extend<T: Clone> Wrapper<T>: Clone { .. }
//   emit Copy::derive(Wrapper, .{ .0 = T });    // extend<T: Copy>  Wrapper<T>: Copy;
```

The keyword and `copy?` expand before that step. `copy` is `derives Clone, Copy`, so each `derive` receives the empty
flow. `copy?` is `derives Clone(..), Copy(..)`, and the compiler resolves each `..` **before** it calls `derive`, once per
aspect. The deriver never sees `..`, and it cannot ask whether a field type implements an aspect: it emits the bounds and
the ordinary checks decide. That keeps derivation independent of the order of impls and rules out cycles.

<!-- doc-example: skip reason="a design under review (RFC-0244, RFC-0238): copy? is not in this release" -->
```metel
copy? struct Boxed<T> { value: T }
//   Clone flow = {T}, Copy flow = {T}  ->  Clone::derive(Boxed, .{ .0 = T }),  Copy::derive(Boxed, .{ .0 = T })

copy? struct View<T> { r: &T }
//   both flows are empty               ->  Clone::derive(View, .{}),           Copy::derive(View, .{})
```

The reason to build it this way is that a library can make its own aspect derivable, and a derivation can take arguments
besides the flow. A serialization aspect might take a name and a type parameter list, and a clause would read:

<!-- doc-example: skip reason="a design under review (RFC-0238, RFC-0246): derivations with arguments do not exist yet" -->
```metel
extend Serialize: Derivable {
    type Args = .{ .0: String, .rename_all: String = "none", ..Flow };
    comptime fun derive(Target: type, args: Self::Args) -> Decl { /* reads typeinfo(Target) */ }
}

struct Item<T> derives Serialize("item", rename_all = "camel", T) { v: T }
//   emit Serialize::derive(Item, .{ .0 = "item", .rename_all = "camel", .1 = T })
```

Several things in this sketch are not settled: what exactly a flow entry's type is, whether a deriver returns a declaration
or calls `emit`, the body of `field_wise`, and how a flow can come after leading positional arguments. That last one
needs a way to number a row's labels after the ones before it, which the design for variadic generics (RFC-0125) records as
not yet built, or a rest parameter (RFC-0247).

## Prior art that shaped it

The model was checked against how other languages decide whether a value is copied implicitly before it was settled. The
repository keeps a survey of that (`architecture/reports/copy-clone-prior-art-survey`). It asks every language the same five
questions: what the default is, how a type opts in or out, where that is written, whether user code can run during an
implicit copy, and what the explicit way to duplicate is. What each answer contributed:

**Rust: the pair, and a sealed copy.** Rust's `Copy` is for "types whose values can be duplicated simply by copying bits",
and its behaviour "is not overloadable". `Copy` requires `Clone`, a field that is not `Copy` is an error, and the standard
documentation says that implementing `Copy` "is part of the public API of your type". Metel keeps the two-level pair and the
sealed bit copy. It also takes Rust's documented pain as an input. `derive` puts a bound on every type parameter whatever the
fields hold, so `&T` ends up requiring `T: Copy` ([rust-lang/rust#26925](https://github.com/rust-lang/rust/issues/26925)). The
proposed fix, [perfect derive](https://smallcultfollowing.com/babysteps/blog/2022/04/12/implied-bounds-and-perfect-derive/),
computes the obligation from the field types, which is what a computed flow does. Rust treats `Copy` as public API, which is
why a `pub` generic type here has to state its flow. Metel departs from Rust in two places: the grant lives on the declaration,
not in an impl anywhere in the crate, and the `Clone` of a `Copy` type is the compiler's. Rust documents that the two should
agree, and cannot enforce it.

**Swift: copyability is fixed on the declaration, and conditions are narrow.** A Swift struct opts out with `~Copyable` on its
declaration, never in an extension. Conditional copyability exists, but [SE-0427](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0427-noncopyable-generics.md)
restricts it hard: the conditions "must be of the form `T: Copyable` where `T` is a generic parameter of the type", the extension
must be in the same file as the type, and it is not allowed on a type with a `deinit`. `BitwiseCopyable` (SE-0426) is the closest
precedent for a sealed implicit copy that needs a declaration-level authorisation. The flow in `derives Copy(T)` is the same
restricted shape.

**Mojo: two levels, one definition of the copy.** In v0.25.6 Mojo reversed its model. `Copyable` now means a value can be copied
explicitly with `.copy()`, and `ImplicitlyCopyable` is a method-less marker that refines it, so that compiler-inserted copies
are opt-in. The stated reasons were a long-standing problem of Mojo "effectively forcing implicit copyability upon all types",
and ensuring "only one definition for the logic of how a type is copied" ([release notes](https://mojolang.org/releases/v0.25.6/)).
That shape, an explicit level and a method-less implicit marker that requires it, is what `Copy` requiring `Clone` gives. Mojo's
rule for closures also matches the one here: a closure is `Copyable` when every value it captures is.

**C++, D and Nim: user code at the copy, which was deliberately not followed.** These languages, and Mojo's copy initializer, let
a type run its own code during an implicit copy. Rust, Go, C# and Swift structs do not. Metel follows the second group. A hook
that runs user code makes the compiler's insertion and removal of copies observable, and three adversarial reviews of the
design kept finding that cost.

Every finding above is marked in the survey as verified (read in a primary document), from memory, or unconfirmed. The C++
and C# entries are the ones from memory; the rest of what is cited here was read in the sources.

## What this model cannot say

The price of putting the condition on the declaration, and of stating it as a list of parameters, is a smaller language of
conditions than Rust has.

**`Copy` only when `T` carries some other marker.** In Rust this compiles:

```rust
trait Marker {}
#[derive(Clone)]
struct Token<T>(T);
impl<T: Copy + Marker> Copy for Token<T> {}   // Token<T> is Copy only when T is Copy and T: Marker
```

The same shape in Metel is rejected, because `Copy` is granted only in the declaration:

<!-- doc-example: expect-fail reason="the extend is the error the example shows: Copy is granted in the declaration, not by extend (T0045)" -->
```metel
aspect Marker {}
struct Token<T> { v: T }
extend<T: Marker> Token<T>: Copy;   // error: `Copy` is a `declared` aspect: grant it in the declaration of `Token`
```

The declaration itself can only say "`Copy` when these parameters are `Copy`", and the bound it puts on each parameter is the
aspect being derived. A condition on some other aspect has no spelling. Swift has the same limit: the proposal says it "is not
permitted to make `Copyable` conditional on any other kind of requirement" than `T: Copyable`. RFC-0224 records the Metel
case: the practical routes are a newtype that is itself `copy`, or putting the marker bound on the functions that use the
type. A bound on the type's own parameter (`struct Token<T: Marker>`) is not the same thing. It restricts which `Token`s exist,
and says nothing about when one is `Copy`.

A few other things the model cannot say:

- **A field whose copyability depends on an associated type.** `value: T::Item` in a `Copy` declaration is rejected, and so is a
  parameter of row or record kind in the flow.
- **A copy that does something.** A type whose copy has to do work, such as bump a reference count, cannot be `Copy`. It
  implements `Clone` and is copied with `.clone()`. C++, D, Nim and Mojo can run code at the implicit copy. Here that is
  closed, on purpose.
- **A `Copy` type with a destructor.** `Copy` and `Drop` cannot be granted to one type. Rust forbids the pair, and Swift forbids
  conditional copyability on a type with a `deinit`.
- **`Copy` granted somewhere other than the declaration.** There is no `extend` of a type from another module to make it
  `Copy`, so a library cannot add `Copy` to a type it does not own.

## Why that trade

**Regularity over width.** RFC-0224 records that in Swift's second review of SE-0427 the main criticism of the `where` rule was
that it is one more special case, not that it was too narrow, and it draws the same conclusion: the regularity of the rule
matters more than its width. (That summary comes from the RFC's own evidence section, which says it was read from search
snippets and not from every page.) A condition that is one shape, a list of parameters, is one rule to learn and to check.

**A condition that names parameters can be stored and checked without a search.** The interface a type publishes is finite and
acyclic, so a use site reads it and substitutes arguments, and nothing runs a solver there. A general solver for exact
conditions was estimated, in a spike, at fifteen to thirty engineer-days (`metel-core#1810`). The design records the route to
it as an end state, with the stored interface as what everything reads, and does not need it to be correct today.

**A public interface that does not move with its fields.** Because the flow is written in the declaration, and a `pub` generic
type has to state it, a field edit that would change what the type promises is an error at the declaration and not a surprise
at a distant use.

**Nothing found that asked for the wider form.** In November the language owner decided that a `Copy` narrowed by an arbitrary
policy is not a requirement, and RFC-0224 records the evidence. Searches found no Rust issue, post or thread asking for
`impl<T: Copy + Marker> Copy` or showing real use of it. In Swift, the one thread about conditional `Copyable` conformances
asks for a shorter spelling, and none of the posts asks for conditions on something other than `Copyable`. That is an absence in
a limited search, and it is not proof that nobody wants it. The pain that is documented runs the other way: derive
over-constraining, which a computed flow fixes. If the demand shows up, the narrowness can be revisited with evidence in hand.

## What is not in 0.16.0

- `.[expr]` label variables are not part of this release. The minting form belongs to RFC-0114 and is
  not implemented.
- An experiment with constructor-call syntax for structs is withdrawn. Structs, named records and
  variants with fields still use braces, `Point { x = 1, y = 2 }`. Keyword arguments on ordinary
  functions are unaffected.

## Upgrading

Everything breaking in this release is a spelling, and the old spellings fail with a message naming the
new one. In order of how much of your code each touches:

1. `:=` for reassignment becomes `=` (`assign_migrate`, run under the old grammar).
2. Row labels get their dot (`label_migrate`), and an anonymous record literal becomes `.{ ... }`.
3. `public` becomes `pub`.
4. `extend T: Copy;` moves to the declaration (`T0045` tells you how).
5. `derives X via T` becomes `derives X(T)`.

Both migration tools are parser-driven, not regexes. The repository's own sources, fixtures and
documentation were moved with them, which is how I know they are safe to run on a real codebase.

The full list, with the issue behind every item, is in the [changelog](/docs/release-notes/changelog).
