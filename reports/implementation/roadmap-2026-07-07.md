# Implementation Roadmap: Lifetimes, Allocators, Borrow-Checking, Type-System Completeness

*This is not a new plan — it reconciles `rfc-implementation-breakdown-2026-07-01.md` (the
concrete phase/RFC breakdown) with `strategy/integrated-language-overview-2026-07-07.md` (the
newer L0–L4 maturity framing and Phase A/B/C recommendation) into one sequencing, checked
against the current state of `metel-core` and the Plane board. Where the two source docs agree,
this doc just restates the consensus in one place. Where they use different phase labels for the
same work, both labels are given so this doc can be cross-referenced against either.*

---

## 1. Where the implementation actually stands today

Surveyed directly against `metel-core/metel-interpreter` (v0.9.1, tree-walking Rust interpreter:
PEG parser → name resolver → path normalizer → two-pass HM typechecker → elaborator → evaluator).

| Area | Status | Evidence |
|---|---|---|
| **Type system (L0)** | Mature, actively developed | HM inference, generics via monomorphization, aspects (traits) with default methods and bounds, ADTs, exhaustive matching, module system all implemented. Single known gap: generic `impl<T>` blocks (`src/typechecker/registry.rs:341`, `// TODO(generic-impl)`). |
| **Ownership / move semantics (L1, RFC-0071)** | Accepted design, **0% implemented** | Evaluator deep-clones every value on bind; no move-once, no `Copy`/`Drop`, no drop glue. |
| **Allocators + lifetime anchors (L2, RFC-0063/65/66/67/68/73/77/74/75/76)** | Fully designed via the "split model," **0% implemented** | No `@a T`, no `&r T`, no allocator types, no `Rc`/`Arc` as language-visible types. `grep` for `allocator`/`region`/`lifetime`/`linear`/`affine` across `src/` returns nothing relevant. |
| **Borrow checker** | Not a separate RFC — it's the new pipeline stage that RFC-0063 introduces | Doesn't exist yet in any form. Called out in the breakdown doc as *"brand new — the largest single piece of work in the whole effort."* |
| **Linear/structural types (L3)** | Exploration only, no RFC | `reports/substructural-types/*` — six open design threads, no ratified syntax. |

**Net read:** everything below the type system is greenfield. There is no partial borrow-checker or
half-built allocator to extend — this is new subsystem construction, not completion of existing
work.

## 2. The phased plan

Five phases (0–4, from the breakdown doc) grouped into three stages (A/B/C, from the integrated
overview). Stage boundaries are where the project should pause and let real implementation
feedback inform the next stage, rather than continuing to design ahead of running code — this is
flagged in the integrated overview as the single highest-derailment-risk item right now ("design
is ~2 threads ahead of running code").

> **Amendment 2026-07-20 — the allocator cluster is re-sequenced to last, and split from
> the borrow checker.** This roadmap's original Phase 3 batched "allocator system + borrow
> checker" together and planned to ship affine-only, brand-free stdlib allocators as part of
> the Stage A MVP, with the full substructural tower (records/linear/brands) deferred to
> Stage B *after* it. That ordering is superseded. Per
> `reports/substructural-types/allocators-as-emergent-synthesis.md` and
> `reports/strategy/OBJECTIVES.md` Priority 3, the allocator feature is not a primitive: it
> decomposes almost entirely into **context parameters + brands + an owned box + the borrow
> checker**, with only the `Alloc` aspect and `@`-sugar as irreducibly allocator-specific
> residue. Two consequences for sequencing:
>
> 1. **The borrow checker and lifetime anchors stay in Phase 3 and stay in Stage A** — they
>    are genuine primitives the whole language needs, gated only on Phase 2 (move semantics),
>    and are *not* held back by anything below. Phase 3 is narrowed to exactly this: the new
>    checker pipeline stage + RFC-0067 lifetime anchors, no allocator cluster.
> 2. **The allocator cluster (RFC-0063/0065/0066/0068/0073/0077) moves out of Phase 3 to a new
>    Phase 5, after the substructural tower**, and is gated on *all* of: the borrow checker
>    (Phase 3), records/views, linear types, lifetime anchors, and brands — plus a
>    context-parameter feature that **has no RFC yet** and is now on the critical path (see the
>    new prerequisite note under Stage B). This is intentional, not a delay: allocators are
>    downstream of those by construction because they are largely built *out of* them. It also
>    matches what the public blog already tells readers (the deepest ownership/allocation model
>    is ahead of the runtime on purpose).
>
> The allocator RFCs are **not** refused, gutted, or superseded by this — they are reframed as
> the *acceptance test* the primitives must reconstruct (can `Heap`/`BumpAlloc`/`@a T`/
> disjointness/sendability be rebuilt from context-params + brands + box + borrow-checker?),
> kept intact as the concrete target that keeps the primitive work honest. See Trigger 18 in
> `OBJECTIVES.md`. The phase text and dependency map below are annotated inline to match; where
> the 07-07 original and this amendment disagree, the amendment governs.

### Stage A — settle the text, ship the MVP (Phases 0–4 below)

**Phase 0 — Foundations**
- Ratify the split model: land RFC-0088 (or amend RFC-0063 directly) and formally sweep
  RFC-0063/65/66/67/68/73/77 from under-review to accepted. Mechanical — "a formality that does
  not block work" — but implementation shouldn't start against unsettled RFC text.
- **Decision: linear types are not a dependency of the allocator cluster.** The prior draft of
  this roadmap (and RFC-0063 §9 item 5) treated "partial consumption of a linear struct" as a
  real-deadline blocker on Phase 3. That's dropped: Phase 3 ships allocator teardown under
  affine-only semantics (RFC-0071 drop glue — a value is dropped at most once, on scope exit or
  explicit `drop`), with no `.free()`-as-sole-discharge linear discipline and no residual-extraction
  mechanism to design. This also resolves RFC-0063 §9 item 1 (affine vs. linear teardown) in favor
  of affine, and moots item 2 (`drop` vs. linear teardown interaction) entirely. Anything that
  actually needs linear (use-exactly-once) semantics for a struct field — including the
  partial-consumption question itself — is deferred whole to Stage B alongside the rest of the
  substructural-types tower; it is not reintroduced piecemeal to unblock Phase 3.
- Cross-cutting prerequisites (do these first, they unblock everything else):
  1. **Impl-resolution refactor** — replace the string-keyed `impl_aspect_env`
     (`src/typeinference/mod.rs`) with a structured `ImplKey{aspect: DefId, type_head, type_args,
     bounds, polarity}`. Called *"the single biggest static prerequisite."*
  2. `DefId`/module-id plumbing for orphan-rule classification.
  3. New coherence pipeline stage (collect impls → orphan filter → overlap scan → auto-impl
     synthesis → freeze registry), inserted between name resolution and typecheck.
  4. AST generalizations shared across many RFCs: `Bound{polarity}`, `TypeRef{structural, dyn,
     projection}`, `ImplBlock{...}`.
  5. `SymbolId` stabilization pass *after inference* — coherence queries, associated-type
     projection, negative-impl lookup, and region-wellformedness checks all lean on symbol
     identity being stable.
- Mechanical, parallelizable, no dependencies: RFC-0084 (`T[N]`), RFC-0083 (`pub let`) — these
  unblock `std::mem::heap`/`local_heap` stdlib modules later.

**Phase 1 — Static type layer (Cluster A)**
Order: `0060 → 0036 → 0072 → 0081 → 0082 → 0061 → 0037`, plus **RFC-0067a** (accepted
2026-07-07, no ordering dependency on the rest of this list — implementable any time). RFC-0067a
is a split-off of the original RFC-0067: `&T`/`&var T` replacing `*T`/`*mut T`, plus auto-deref,
with no lifetime anchors and no allocator-pointer interaction. It has zero dependency on affine
types or the borrow checker — anchors and allocator interaction stayed behind in the (still
under-review, still Phase 3) remaining RFC-0067, since tracking anchor scope validity *is*
borrow-checker work, not just a consumer of it. Gated on RFC-0060 (coherence + impl-resolution
refactor from Phase 0). Entirely runtime-independent — can proceed without waiting on Phase 2/3.
RFC-0008 (`dyn Aspect`) is *not* in this batch — it needs fat pointers and is deferred to Phase 4.

**Phase 2 — Ownership & value-representation overhaul**
RFC-0071: affine-by-default values, `Copy`/`Drop` opt-in and mutually exclusive, drop order,
explicit/partial drop. Requires changing the evaluator's binding semantics from deep-clone-on-bind
to move-on-bind plus drop glue. Flagged as *"the dominant runtime risk"* — this ripples through
the entire evaluator, not just new code paths.

**Phase 3 — Borrow checker + lifetime anchors (Cluster B core)** *(narrowed 2026-07-20 — the
allocator cluster moved out to Phase 5; see the amendment above)*
Order: the borrow/lifetime checker stage → `0067` (lifetime anchors). `0067` here is the
narrowed RFC-0067 (lifetime anchors, move-out) that remains after RFC-0067a split off into Phase
1 — it builds directly on RFC-0067a's `&T`/`&var T` without changing that syntax. This is where
the new pipeline stage gets built: lifetime-anchor tracking, borrow exclusivity, wellformedness,
move/affine tracking. `Outlives` is explicitly *not* a solved constraint here — it's derived
structurally from scope nesting, which is part of why the old region-parameter model (see §4) was
abandoned. The borrow checker is a genuine primitive the whole language needs (records, allocators,
and safe references all check against it), so it stays in Stage A, gated only on Phase 2 — it is
*not* held back by the allocator re-sequencing.

RFC-0066 (allocated value extraction) moves with the allocator cluster to Phase 5 — its `@a T`
→ `T` move-out only has meaning once `@a T` exists, which is now downstream of the tower. The
borrow checker itself does not need it to be built.

This phase (the checker stage + `0067` lifetime anchors) no longer waits on any linear-types
decision — see the Phase 0 note above. It still waits on Phase 2 (RFC-0071) landing, since the
borrow checker needs move-on-bind semantics to check against.

**Phase 4 — Convergence** *(narrowed 2026-07-20 — RFC-0074 moved to Phase 5)*
Order: `0080 (stdlib aspects) → 0008 (dyn Aspect)`. These are capstone items that need Cluster A
(coherence, negative impls, associated types) complete. **RFC-0074 (Rc/Arc) moved to Phase 5**
in the 2026-07-20 amendment: it was already blocked on RFC-0076 (brands) resolving its own open
question (Q1), so it belongs with the rest of the brand-dependent allocator/shared-ownership work
downstream of the substructural tower, not in this Stage A convergence phase. `Rc`/`Arc` are
themselves a good secondary instance of the Phase 5 synthesis question — a shared-ownership box
carrying a brand — which is further reason to build them alongside the allocator cluster rather
than ahead of it.

### Stage B — the substructural tower, now on the allocator critical path

Don't design further here until Stage A produces running programs. Then:
- Test whether linear types earn their implementation cost against real code (collections, `?`
  propagation, closures are the open questions — closures were "refused with no replacement," which
  is itself a data point).
- Mature brand inference (RFC-0076) using real usage patterns rather than speculation.
- Only pull open-row generics (`<row R>`) forward if there's genuine demand — the recommendation
  across every doc surveyed is closed `record` types first.
- **Records/views (RFC-0090/0091), linear types (RFC-0089), and brands (RFC-0076)** are no
  longer purely feedback-gated "nice to have if justified" work — per the 2026-07-20 amendment
  they are load-bearing *prerequisites* for the allocator cluster (Phase 5). They are still not
  to be designed speculatively ahead of Stage A feedback; the change is only that allocators
  now cannot precede them, not that they should be rushed.

> **New prerequisite, 2026-07-20: context parameters.** The allocator decomposition
> (`reports/substructural-types/allocators-as-emergent-synthesis.md`) identifies a *general*
> context-parameter feature (a value a call tree needs, resolved by type from scope, ambiguity
> an error — of which the allocator handle `(@a: A)` is one instance) as a primitive the
> allocator ergonomics are built on. It has **no RFC anywhere in the corpus** — the single
> largest unwritten hole on the allocator path, larger than any open brand or borrow-checker
> question. Writing a context-parameter draft RFC (explicitly general, not allocator-only, with
> the by-type/ambiguity-is-error resolution rules RFC-0065 §1/§1b already prototype in
> allocator-specific form) is the first concrete action this re-sequencing calls for.

### Phase 5 — Allocators, as the synthesis test *(new, 2026-07-20; formerly Phase 3's allocator half)*

Gated on **all** of: Phase 3 (borrow checker + lifetime anchors), records/views, linear types,
brands, and the new context-parameter feature. Order within the cluster is unchanged from the old
Phase 3 (`0063 → 0066 → 0065 → 0068 → 0077 → 0073`), but the cluster as a whole now runs *after*
the substructural tower rather than before it.

The framing is different from "implement the allocator RFCs": Phase 5 is where the falsifiable
question gets answered — **can `Heap`, `BumpAlloc`, `@a T`, disjointness, and sendability be
rebuilt as (context parameter) + (allocator-instance brand) + (owned box) + (borrow-checked
lifetime), leaving only the `Alloc` aspect and `@`-sugar as allocator-specific residue?** If yes,
most of the allocator cluster is sugar + library over primitives already built in Stages A/B, and
the language stays small. If no, the part that resists the rebuild is exactly the genuinely
allocator-specific machinery worth keeping as a dedicated feature. Either answer is a win; the
allocator RFCs stay intact throughout as the concrete acceptance test (never gutted — see the
amendment and `OBJECTIVES.md` Trigger 18).

Stdlib allocators (`Heap`, `LocalHeap`, `BumpAlloc`, `AutoAlloc`) still don't need a Metel-level
unsafe layer to land — they can be host-implemented in Rust behind the existing
`native(@std.core...)` pattern already used in `core.mtl`. That defers the unsafe-primitive layer
(Stage C, below) without blocking user-visible allocator functionality.

### Stage C — frontier, gated on prerequisites not yet met

Nothing here blocks Stage A or B; sequence-agnostic until its own gate opens:
- **Low-level allocator API + unsafe-primitive layer** (RFC-0063 §9 items 3–4) — only gates
  user-authored custom allocators. Revives RFC-0026, which is currently written against the
  refused RFC-0028 pointer model and needs a rewrite before it's actionable.
- **RFC-0075 (region-inference / `AutoRegion` elision)** — explicitly speculative without
  implementation experience; wait for real annotation-burden data from Stage A before touching
  this.
- **Rest of the substructural-types tower** — structural records as a type former, open-row
  generics, structural typestate, brand-kind unification. Exploration-only; no RFC yet.
- **Effects** — no RFC exists yet. Flagged in the integrated overview as *"most load-bearing,
  least baked"* — needs continuation-capture the runtime doesn't have.
- **Concurrency beyond `spawn` + `Chan<T>` + `select`** — fork-join (`||`) is retracted for good
  (RFC-0064), not deferred. No in-place parallelism story over arena data; revivable only on real
  workload demand.

## 4. Why the old region/lifetime-parameter model was abandoned

Relevant background for anyone picking up RFC-0025/0028/0046/0047/0048/0051/0056/0069/0085/0086/0087
(all now in `internal/rfcs/5-refused/`) expecting them to be live — they aren't.

The unified model gave one concept, `Region`, triple duty: lifetime tag, disjointness proof, and
allocation strategy. That only held if a value's lifetime always equaled its region's lifetime.
RFC-0066 (individual move-out/drop from a region) broke that premise: a region-allocated value can
be moved out or dropped while the region continues holding other allocations, so a value's
lifetime and its allocator's lifetime are provably two different things. Patches within the
unified model (`PhantomRegion`, universal own-regions) stretched `Region` past a coherent meaning
and produced real conflations (ambiguity between allocator-tag and pseudo-lifetime on the same
value).

The fix: split into two orthogonal concepts — **allocators** (first-class values, `@` prefix,
`Heap`/`BumpAlloc`/etc., live in the value channel) and **lifetime anchors** (compile-time
parameters, `&` prefix, always named after a real binding rather than an abstract `'a`, live in
the type channel). This let four RFCs retract cleanly as one consequence rather than four separate
fixes, which is read as strong evidence the new frame is correct. It also keeps diagnostics
concrete — because anchors are named after real bindings, errors can say "escapes the lifetime of
`r`" instead of Rust's abstract `'a`.

**Stale item to flag:** `rfc-0052-lifetime-system.md` still lives in `0-draft/` but is not part of
the active cluster — it predates the split (created 2026-06-05, on hold 2026-06-13, before the
2026-07-02 split), still uses pre-split syntax (`*'a T`, `'r`), and cites now-refused RFC-0025/0051
as prerequisites. No supersession note exists in the file itself. The live lifetime-anchor design
is in RFC-0067, not RFC-0052. Worth either formally superseding RFC-0052 or moving it to
`5-refused/` alongside the RFCs it depends on, so it stops reading as active scope.

## 5. Risk register (merged, deduplicated)

Ordered by derailment potential, not implementation depth:

1. **Design running ahead of implementation.** The integrated overview's own top risk. The
   antidote is executing Stage A, not producing more design docs — this roadmap intentionally
   stops short of resolving Stage B/C open questions for that reason.
2. **Deep-clone-on-bind → move-on-bind conflicts with the entire evaluator.** Phase 2's "dominant
   runtime risk" — every place that currently relies on implicit copying needs an audit.
3. **The borrow/allocator checker is brand new.** No prior art in this codebase to extend; Phase 3
   is the single largest piece of work in the whole effort.
4. **Wellformedness vs. variance pull in opposite directions** (RFC-0077 §4.3) — flagged as the
   most error-prone interaction in Cluster B.
5. **`AutoAlloc` is under-specified** (RFC-0073 UQ1/2) — risk of a fallback that's sound but
   misleading to users.
6. **Sendability auto-impl vs. negative impls** (RFC-0074 §2.6) — without correct negative impls,
   `Rc<T>` would silently become `Send`, which is a data-race bug, not a type error.
7. **Brand identity is pervasive and inference is immature** (RFC-0076 Q3) — `@a T` distinguishes
   allocator *instances*, not types, which is unusual for a typechecker and touches type equality,
   hashing, and caching broadly.
8. **Linear-type-tower viability is unproven** — collections, `?`/early-return, and closures (no
   replacement after refusal) are all open against real code, not just design. No longer a Cluster
   B risk following the Phase 0 decision to decouple linear types from the allocator cluster
   entirely — this is now purely a Stage B concern. **Amended 2026-07-20:** the Phase 0 decoupling
   was about the *old* affine-only, brand-free MVP allocators (the ones that were to ship in the
   original Phase 3); it stands for those. But the allocator re-sequencing puts the *full*
   allocator cluster (Phase 5) downstream of the whole substructural tower, so linear-tower
   viability is once again on the allocator critical path — not for an MVP allocator (there
   isn't one anymore), but for allocators at all. The risk is unchanged in substance; what
   changed is that "Stage B doesn't pan out" now blocks allocators rather than merely delaying an
   optional tower, which *raises* this item's stakes even though it stays a Stage B concern.
9. **Ergonomic cost for library authors may be under-counted** across the allocator/lifetime
   surface syntax.
10. **Effects have no RFC and need continuation-capture the runtime doesn't have** — least baked,
    most load-bearing item in the Stage C frontier.

## 6. Plane board cross-check (findings only — board not modified)

The board (`METEL` project, 193 work items) was checked against this roadmap. It has not been
updated to reflect the split model:

- **Stale in-progress/backlog items tied to now-refused RFCs** (should be cancelled or
  re-pointed): METEL-16 ("Region Allocation," RFC-0025, currently *In Progress*), METEL-127/141
  ("Linear Closure Capture," RFC-0046, duplicated), METEL-129/143 ("Region × Pointer Interaction,"
  RFC-0048, duplicated), METEL-131/145 ("RegionFree Exit Constraint," RFC-0051, duplicated),
  METEL-139 ("Explicit Region Parameters," RFC-0056). All five RFCs are in `5-refused/`.
- **Ambiguous status:** METEL-130/144 ("`linear fun` Type System," RFC-0052 — RFC-0049 is still
  formally `0-draft`/on hold, not refused, but per §4 above it isn't part of the active cluster
  either). Worth a status decision rather than a blanket cancel.
- **Zero board coverage** for the entire active cluster: RFC-0063, 0065–0068, 0071–0077, 0088, plus
  the Phase-1 items RFC-0072/0081/0082. RFC-0071 (ownership/move semantics) — foundational to
  everything in Phase 2 onward — has no work item at all.
- Phase-1 items that *do* already exist on the board: RFC-0036 (METEL-86), RFC-0037 (METEL-87),
  RFC-0060 (METEL-186), RFC-0061 (METEL-189) — all correctly in Backlog.

Recommendation: treat Plane-board reconciliation (cancel the stale six, create tickets for the
~18 untracked RFCs, grouped by the phases above) as a Phase 0 task in its own right, since anyone
scanning the board today would reasonably conclude the old region-parameter model is still being
built. This was scoped out of this pass at the user's request and is ready to run as a follow-up.

## 7. Open questions carried forward (not blocking, tracked for visibility)

From RFC-0063 §9: item 5 (partial consumption of a linear struct) and item 1 (allocator teardown
discipline) are both resolved by the Phase 0 decision above — affine-only teardown, no linear
discharge, partial consumption deferred whole to Stage B. Item 2 (`drop` vs. linear teardown) is
moot for the same reason. What's left has no urgency and is safe to leave open through Stage A:
- `Alloc.alloc` method signature — unspecified.
- Custom-allocator unsafe-primitive layer — blocked on reviving RFC-0026 against a pointer model
  that isn't refused (see Stage C).
- Multi-anchor borrows (`&r,s T`) — "no other part of the model depends on this."
- Ratification vehicle: new RFC-0088 vs. direct amendment of RFC-0063 — undecided, doesn't block
  Phase 0 either way.
